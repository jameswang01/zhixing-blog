## 2 JVM 与诊断

### 19 JDK 8 为什么用元空间替代永久代

**理解与追问：** 永久代存放类元数据的旧设计受固定容量等问题困扰，HotSpot 在 JDK 8 将相关元数据迁至本地内存中的元空间。元空间仍有上限和耗尽风险，类加载器泄漏也不能被忽略。

方法区是 JVM 规范中的逻辑区域,永久代和元空间是 HotSpot 在不同版本中的实现方案。JDK 8移除永久代,将类元数据放到本地内存中的元空间,减少永久代容量预估和调优的负担,并改善类元数据的内存管理;这并不意味着方法区消失。

- 元空间不受 Java 堆的 -Xmx 直接限制,但仍受本机或容器可用内存及 MaxMetaspaceSize 等限制,也会发生 OOM。

- MetaspaceSize 主要是触发相关 GC 的初始高水位阈值,不是元空间最大容量。

- 类卸载时可回收对应元数据;类加载器泄漏仍可能导致元空间持续增长。

**易错提醒：** 元空间不是无限内存,也不能简单说成“把整个方法区原样搬到堆外”。

**具体场景：** 应用频繁生成或加载类，而旧类加载器被线程或静态引用持有，相关元数据可能无法卸载，元空间持续增长。排查时应结合类加载数量和类加载器保留情况，而非只调大 Java 堆。

**追问：元空间在本地内存，是不是无限的？** 不是。它受到进程、容器及相关 JVM 参数约束；动态生成类或类加载器无法回收时仍可能耗尽。排查要结合类加载数量与内存证据。

### 20 Tomcat 为什么自定义类加载器

**理解与追问：** Web 容器需要让不同应用使用不同版本的依赖，并隔离应用之间的类。判断类型是否相同，除了类名还要看定义它的类加载器；因此同名类跨加载器转换可能失败。

Tomcat 为不同 Web 应用创建独立的类加载器,使各自 WEB-INF/classes 和 WEB-INF/lib 中的类库互相隔离,并通过公共父加载器共享容器类库。重新部署时可创建新的应用类加载器,加载新版本类;JSP 的更新还依赖编译及专用加载流程。

- 应用类默认倾向于先查自身,但 JRE 基础类和 Tomcat 实现的 Servlet、JSP 等 API 有优先委派例外;delegate=true 可调整普通查找顺序。

- 类身份由类名与定义它的类加载器共同确定,同名类未必能互相转换。

- 旧应用的线程、ThreadLocal 或静态引用若仍可达,旧类加载器就可能无法回收。

**易错提醒：** 不能说 Tomcat 对所有类都完全打破双亲委派,或同一加载器可随意重载同名类。

**具体场景：** 两个 Web 应用各带不同版本的同名库类，容器通过各自类加载器隔离。相同类名由不同加载器定义时是不同类型，直接跨应用强制转换可能产生 ClassCastException。

**追问：同名类为什么可能不能互转？** Java 类型身份由类的二进制名称和定义它的类加载器共同确定。不同 Web 应用分别加载同名类时，即使字节码相同，也可能是不同类型。

### 21 Java GC 的基本过程怎样回答

**理解与追问：** 先区分对象分配、存活对象判定、回收与整理，再说明所选收集器。不要把 Minor GC、Full GC 的触发与动作绝对化，具体还要看 JVM、收集器和配置。

先从 GC Roots 出发识别可达对象,再按具体收集器算法回收空间。常见算法有标记清除、复制和标记整理:清除释放垃圾空间,复制或整理会移动存活对象并更新相关引用。不同收集器的阶段、并发方式和停顿点不同,没有所有 GC 都完全相同的固定流程。

- GC Roots 包括活动线程栈中的引用、JVM 内部持有的引用等;循环引用如果整体不可达,也可以回收。

- 并发标记需要处理应用同时修改引用的问题;“并发收集器”也可能包含 Stop-The-World 阶段。

- 对象分配不是所有 GC 最后统一执行的一步;不可达也不保证立刻回收,外部资源应显式关闭。

**易错提醒：** 不是每次 GC 都整理整个堆,也不是所有对象都必须从年轻代进入老年代。

**具体场景：** 对象 A 和 B 相互引用，但从任何 GC Roots 都不能到达它们时，循环引用本身不阻止回收。相反，一个大集合仍被静态变量引用时，其中对象可能持续可达；何时回收还取决于收集器。

**追问：循环引用会不会永远无法回收？** 关键是能否从 GC Roots 到达，而不是对象之间是否互相引用。一个不可达的对象环也可回收；具体停顿和回收范围取决于收集器。

### 22 G1 怎样尽量控制停顿时间

**理解与追问：** G1 把堆划分为 Region，并估算各区域回收收益和成本以安排回收。目标停顿时间是尽力满足的目标，不是硬实时保证；大对象、分配速率和存活率都可能影响结果。

G1 将堆划分为多个 Region,根据历史停顿、存活对象量和回收成本建立预测模型,并调整年轻代规模及混合回收所选的老年代 Region,在目标预算内尽量获得较多可回收空间。MaxGCPauseMillis 是软目标,不能保证每次停顿都不超过它。

- 年轻代回收主要处理年轻代 Region;并发标记后,Mixed GC 在年轻代之外选择部分老年代 Region,并复制存活对象。

- 回收收益不只取决于垃圾比例,还受到存活对象复制、引用扫描等成本影响;不能简单描述为固定优先队列依次回收。

- 目标过紧可能增加回收频率、降低吞吐;内存不足或疏散失败时仍可能出现长停顿甚至 Full GC,应结合 GC 日志判断。

**易错提醒：** G1 既不是完全无停顿,也不是每次暂停都能任意选择少量年轻代 Region。

**具体场景：** 若目标停顿设为 200ms，G1 会根据历史成本估算待回收区域，但遇到存活对象多或疏散失败仍可能超时。排查时应看对应 GC 日志中的阶段耗时、分配压力与堆占用。

**追问：配置 200ms 停顿目标就一定不超时吗？** 不是。G1 根据历史数据估算并尽量达到目标；存活对象多、疏散失败或系统资源不足仍可能超出，需要结合 GC 日志分析。

### 23 怎样排查 Java 进程 CPU 持续过高

**理解与追问：** 从进程 CPU 到线程，再到多次线程栈：先定位热点线程，再结合线程 ID 查看对应调用栈，判断忙循环、频繁计算或 GC。持续高 CPU 需要结合业务指标和采样，不能单凭一次栈断言根因。

先确认是哪个进程、是否持续高占用,再定位热点线程并结合多次线程栈或采样剖析定位代码。Linux 平台线程场景可用 top -H -p PID 找 TID,将十进制 TID 转为十六进制,与线程转储中的 nid对照;同时区分业务计算、忙循环、频繁 GC 和编译等原因。

- 优先使用匹配版本的 jcmd PID Thread.print -l,多次间隔采集;仅一张 RUNNABLE 栈不能证明死循环。

- 结合 JFR、GC 日志、请求量、分配速率确认热点;堆信息可查看 jcmd PID GC.heap_info,并先用help 核对可用命令。

- top 参数及线程 ID 映射依赖系统;虚拟线程不能直接按平台线程的一对一方式套用,应结合支持虚拟线程的转储或 JFR。

**易错提醒：** jmap -heap 不是所有新 JDK 都适用的通用命令;CPU 高也不等于一定是 GC 或死锁。

**具体场景：** Linux 上先定位 CPU 高的 Java 进程，再用 `top -H -p PID` 找热点线程，将 TID 转为十六进制，对照多次线程转储里的 nid。若是 GC 线程，再结合 GC 日志；单张 RUNNABLE 栈不足以证明死循环。

**追问：线程栈显示 RUNNABLE 就是死循环吗？** 不能单凭一次转储判断。连续采样若热点线程持续停在同一计算路径，再结合 CPU 采样、请求量与 GC 数据，才能逐步缩小范围。

### 24 新增 JVM 运行时内存区域怎样划分

**理解与追问：** 以 HotSpot 为例，堆中通常保存对象实例，虚拟机栈保存线程调用帧；元空间存放类元数据，线程栈和元空间并非普通 Java 堆。直接内存也应计入进程内存排查。

按 JVM 规范,运行时数据区包括程序计数器、Java 虚拟机栈、本地方法栈、堆和方法区;运行时常量池属于方法区。计数器与栈按线程维护,堆和方法区由线程共享。规范描述逻辑职责,不能把某个 HotSpot 版本的物理布局当成所有 JVM 的强制实现。

- Java 方法调用通常建立栈帧,保存局部变量表、操作数栈和动态链接等信息;局部变量里的引用与其指向对象不是同一块存储。堆用于类实例和数组,方法区保存类型等运行时信息;具体内存位置还受实现和优化影响。

- HotSpot 元空间承载类元数据,但 Java 堆、元空间之外还有线程栈、代码缓存、直接内存和其他本地开销。-Xmx 只限制 Java 堆,不能据此推导整个进程的最大内存;递归过深通常首先关注StackOverflowError。

**易错提醒：** “线程私有”描述访问与生命周期归属,不表示栈帧里引用的对象一定只有该线程能访问。

**具体场景：** 容器限额 2GB、Java 堆上限 1.5GB 时，剩余空间还要容纳线程栈、元空间和直接内存等。如果进程总内存超限，可能被系统终止，即使 Java 堆还没有耗尽。

**追问：堆大小等于进程内存吗？** 不是。进程还包含线程栈、元空间、直接内存、代码缓存等开销。容器 OOM kill 也可能没有 Java 层 OutOfMemoryError，需要检查容器和系统事件。

### 25 新增 类加载过程与双亲委派是什么

**理解与追问：** 类初始化阶段执行静态变量赋值和静态初始化逻辑，而不是所有类加载完成就立即运行所有初始化代码。双亲委派是常见模型；自定义类加载器和某些插件体系可能调整委派顺序。

类的生命周期包含加载、链接和初始化等阶段;链接口分验证、准备和解析。加载建立类型的运行时表示,验证检查合法性,准备分配类变量等所需存储,解析处理符号引用,初始化执行类变量初始化器及静态代码块。解析可延迟,不必在初始化前全部完成。

- 默认 loadClass 先检查是否已加载,再委托父加载器,父方无法加载时才调用自身 findClass。它按父加载器引用委派,通常不是类继承关系;该机制减少基础类被重复定义和替换的机会,自定义加载器可在规则约束下改变策略。

- 加载不等于初始化:new、调用类的静态方法、读写非常量静态字段等会按规则触发初始化;读取编译期常量通常不会。ClassLoader.loadClass 通常不初始化,而 Class.forName 的单参数形式默认会初始化;应区分类初始化与对象构造。

**易错提醒：** 类加载、类初始化和执行实例构造器是不同动作,不能说“只要引用类名就执行静态代码块”。

**具体场景：** `ClassLoader.loadClass` 通常只加载而不初始化；`Class.forName` 的单参数形式默认触发初始化。若类有静态初始化块，观察其输出可区分这两个过程；实际行为仍以具体调用方式为准。

**追问：加载和初始化有什么区别？** 加载是取得类定义并建立运行时表示；初始化执行类变量初始化器和静态代码。只获得 Class 引用并不总会触发初始化，具体看使用方式。

### 26 新增 对象创建与内存分配有哪些要点

**理解与追问：** 从分配内存、初始化默认值、设置对象头到执行构造逻辑，可以把对象创建与安全发布分开解释。栈上分配和标量替换属于优化结果，不能把源代码中的 new 一概断言为堆分配。

普通 new 创建对象时,先满足目标类必要的加载、链接和初始化要求,再申请对象存储并使实例字段具有默认值,随后执行相应构造过程。HotSpot 中分配常使用线程本地分配缓冲 TLAB 或受并发保护的共享分配路径;构造器赋值与默认零值初始化要区分。

- TLAB 通常是 Java 堆内划给线程的一块分配区域,用于减少共享分配竞争,不是线程栈;没有TLAB 或空间不足时会走其他路径。分配、回收策略依收集器和参数变化,不能保证所有对象都先进入 Eden 或达到固定年龄才晋升。

- 逃逸分析可帮助 JIT 进行标量替换、消除部分分配和锁,但这依赖编译器实际分析结果,不代表写在方法内的对象就必然分配在栈上。对象从构造器中提前泄露还可能破坏安全发布,不应把引用可见视为构造已完成。

**易错提醒：** 对象的声明位置不直接决定存储位置;引用赋值、内存分配和构造初始化也不是同一动作。

**具体场景：** 多个线程并发创建对象时，HotSpot 可通过堆内的 TLAB 减少共享分配竞争；TLAB 空间不足时走其他分配路径。代码里写了 new 不等于一定能从源码直接断定最终是否保留堆分配。

**追问：TLAB 是线程栈吗？** 不是。TLAB 通常是 Java 堆内供线程快速分配的一块区域；逃逸分析及标量替换属于可能发生的 JIT 优化，不能从代码位置直接断定存储位置。

### 27 新增 怎样诊断 OOM 与频繁 Full GC

**理解与追问：** 先区分 Java 堆、元空间、直接内存及本地线程等不同耗尽类型，保留异常信息、GC 日志和必要转储。Full GC 频繁也可能因分配速率、存活对象或配置问题，并不必然是内存泄漏。

先按错误明细区分堆空间、元空间、直接内存或本地线程等资源耗尽,再结合进程和容器限制定位。频繁 Full GC 应查看触发原因、耗时及回收前后占用,判断是存活集过大、异常保留、分配压力还是配置问题;它不是内存泄漏的充分证据,也不一定已发生 OOM。

- 堆问题可保留 OOM 堆转储并分析支配树、对象数量及到 GC Roots 的保留路径,结合业务生命周期判断引用是否多余;还要检查缓存、队列、监听器及线程上下文。转储可能暂停应用并占用大量磁盘,应按容量和线上影响安排。

- 回收后占用仍高,需区分合理存活数据与异常保留;占用能明显下降却频繁触发,则检查分配速率、晋升与显式 GC 等原因。本地内存问题还需结合线程数、直接缓冲和已启用的 NMT 等证据,单看堆转储可能找不到全部原因。

**易错提醒：** 调大 -Xmx 可能只是延后故障,还会挤占其他内存;操作系统杀进程也未必产生 Java OOM。

**具体场景：** 先看错误是 Java heap space、Metaspace 还是无法创建本地线程。堆问题可结合转储看对象到 GC Roots 的保留路径，再判断缓存、队列或监听器是否超出业务生命周期。

**追问：Full GC 后占用高就一定泄漏吗？** 不是。存活集可能本来就大，也可能存在不必要的长期引用。要结合堆转储中的保留路径和业务生命周期判断，并注意转储对线上资源的影响。
