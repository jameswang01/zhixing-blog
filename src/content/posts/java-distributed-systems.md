## 分布式事务

<span id="73-2pc-是什么-有哪些主要问题"></span>

### 1 2PC 是什么 有哪些主要问题

**理解与追问：** 协调者先询问参与者是否准备提交，再发出提交或回滚决定。参与者准备后可能持有资源等待最终决定，因此要分析协调者故障、超时及恢复过程。

两阶段提交由协调者统一决定多个参与者提交或回滚:先准备并收集投票,再持久化全局决议并通知各参与者完成。

- 准备阶段:参与者执行本地事务、持久化可恢复的准备状态并保留必要资源;返回 Yes 表示承诺之后能按决议完成。

- 决议阶段:所有参与者同意才决定提交,否则在尚未决定提交时决定回滚;决议必须可恢复,通知失败应按既定决议继续恢复和重试。

- 主要代价:多轮通信、日志和锁持有时间;已准备的参与者若无法获知决议,可能阻塞,需要协调者恢复、查询及运维处理。

**易错提醒：** 未收到提交通知可能暂时停留在准备态,规范恢复流程不是让它擅自回滚而造成永久分歧。

**具体场景：** 协调者请求库存库和账户库准备提交；双方准备成功后必须等到最终决议。若协调者失联，已准备的参与者可能继续持有资源等待，恢复流程要依据持久化决议推进。

**追问：参与者准备成功后协调者失联怎么办？** 参与者可能无法独立知道最终决议，因而等待协调者恢复或通过协议查询。提交决议一旦确定，就应按可恢复的既定决议继续执行。

<span id="74-3pc-与-2pc-有什么区别"></span>

### 2 3PC 与 2PC 有什么区别

**理解与追问：** 3PC 增加阶段并使用超时机制尝试降低阻塞，但网络分区等故障假设下仍要仔细讨论一致性。面试时说明其解决目标与条件，不要说它彻底消除了 2PC 的所有问题。

3PC 通常分为 CanCommit、PreCommit、DoCommit,在投票与最终提交之间增加预提交状态,使节点在特定故障假设下更容易判断后续动作。

- CanCommit 询问是否可提交;PreCommit 推进参与者进入预提交状态;DoCommit 根据协议完成不可逆的最终提交。

- 额外状态和通信轮次可以减少部分协调者故障造成的阻塞,但其非阻塞性质依赖网络及时性、故障检测等假设,不能外推到任意异步网络。

- 网络分区或无界延迟下,超时无法可靠区分节点宕机和消息延迟;简单“超时就提交或回滚”不能同时保证原子性与可用性。

**易错提醒：** 提交决议已经确定或参与者已经提交后,协调者不能因为 Ack 超时再发 abort 推翻提交。

**具体场景：** 3PC 把准备和最终提交之间的状态进一步细分，试图在特定假设下减少阻塞。但网络分区时超时不能可靠区分节点宕机或消息延迟，因此不能保证任意情况下都无阻塞且一致。

**追问：3PC 为何不能保证任何网络故障下都无阻塞且一致？** 超时无法可靠区分节点故障与消息延迟；其行为依赖网络和故障检测假设，不能把理想条件当成任意分区下的保证。

<span id="75-tcc-是什么-适用于什么场景"></span>

### 3 TCC 是什么 适用于什么场景

**理解与追问：** 例如优惠券或库存可以先冻结，再确认消耗或取消释放。TCC 把业务资源的预留与最终处理显式建模，收益是缩短跨服务持锁时间，代价是状态机、补偿和幂等复杂度。

TCC 将业务拆成 Try、Confirm、Cancel 三个操作:先检查并预留资源,再由全局结果决定确认使用资源或释放预留,是业务层面的两阶段事务方案。

- Try:校验并冻结库存、额度等业务资源,预留动作应在本地事务内完成;预留后的资源不能再被其他事务使用。

- Confirm:把已预留资源转成正式结果;Cancel:释放预留资源,二者都要支持重复调用且相互排斥。

- 适合能够清晰定义预留、确认、取消语义的业务;相比长时间持有数据库事务锁,TCC 转为维护业务冻结状态,但开发、补偿和异常恢复成本更高。

**易错提醒：** TCC 不要求所有阶段共用一个数据库事务,也不能把不可逆的外部操作随意放进 Try。

**具体场景：** 下单时 Try 先冻结 1 件库存；全部参与方成功后 Confirm 转为正式扣减，失败时 Cancel 释放冻结。Confirm 和 Cancel 可能被重复调用，需要状态机与幂等处理。

**追问：TCC 的 Try 阶段能直接执行不可逆操作吗？** 应尽量设计为可确认或可取消的资源预留。对无法撤销的外部副作用，要考虑人工介入、补偿和业务状态，而不是假定回滚一定可行。

<span id="76-tcc-如何处理幂等-空回滚和悬挂"></span>

### 4 TCC 如何处理幂等 空回滚和悬挂

**理解与追问：** 以一条分支记录维护初始、已预留、已确认、已取消等状态，通过条件更新约束合法流转。尤其要考虑 Cancel 先到、Try 后到的乱序，避免资源在事务结束后被错误冻结。

用全局事务 ID 与分支 ID 唯一标识分支,通过持久化状态机、唯一约束和本地事务约束状态转换,确保重复与乱序请求不会重复改变业务资源。

- 幂等:Confirm、Cancel 的应答丢失会触发重试;检查已确认、已取消状态,重复请求返回原结果,不能重复扣减或释放。

- 空回滚:Cancel 到达时 Try 尚未执行或未成功,不应释放不存在的冻结资源;仍需记录已取消或防悬挂标记。

- 悬挂:Cancel 先完成,延迟的 Try 后到;Try 必须检查取消标记并拒绝预留,否则会遗留无法确认或释放的资源。

- 原子性:状态表与冻结、扣减、释放等业务变更放在同一本地事务内,并用锁或条件更新处理并发,不能仅在内存里“先查再改”。

**易错提醒：** 空回滚直接返回成功但不留取消记录,只解决了当次回滚,仍可能发生后到 Try 悬挂。

**具体场景：** Cancel 因超时先于 Try 到达：即使没有冻结记录，也应留下已取消标记；迟到的 Try 检查标记后拒绝冻结，避免事务结束后仍遗留资源。

**追问：Cancel 先到、Try 后到如何防止悬挂？** Cancel 即使没有发现预留资源，也要持久记录取消状态；后到的 Try 检查该状态并拒绝预留，状态与资源变化要有可靠事务约束。

<span id="77-新增-cap-与-base-如何用于系统选型"></span>

### 5 CAP 与 BASE 如何用于系统选型

**理解与追问：** 讨论 CAP 前先明确系统边界、网络分区以及对每个非故障节点响应的要求。业务可按操作分级：资金变更与展示缓存对错误结果和不可用的容忍度不同。

CAP 指出,网络分区发生时,系统不能同时保证线性一致性和每个非故障节点都能成功响应请求。选型应按具体操作判断:资金扣减优先守住一致性,展示数据可容忍短暂旧值。BASE 强调基本可用、软状态、最终一致,需要明确收敛、补偿及冲突处理机制。

- CAP 的一致性指操作看起来按实时顺序发生在单一副本上,不等于数据库 ACID 中的约束一致性;可用性也不等于通常的年度可用率。

- 分区时可拒绝部分请求以保一致,或接受可能冲突的操作再修复;局部事务仍可使用 ACID,跨服务数据再通过可靠事件逐步收敛。

**易错提醒：** CAP 不是任意“三选二”,BASE 也不是放任数据不一致后自动恢复的保证。

**具体场景：** 库存扣减面对网络分区时，如果不能安全确认可用库存，可拒绝或延迟部分操作以守住约束；商品展示的缓存则可能接受短暂旧值。要针对具体操作讨论，而不是给整个系统贴单一标签。

**追问：CAP 的 C 与 ACID 的 C 一样吗？** 不一样。CAP 的 C 讨论一致性模型，ACID 的 C 讨论事务前后是否满足约束；先明确系统边界与具体故障，再讨论取舍。

## 分布式锁与 RPC

<span id="78-如何用-mysql-实现分布式锁"></span>

### 6 如何用 MySQL 实现分布式锁

**理解与追问：** 如果锁记录必须存在，先保证初始化与唯一性，再用事务内的锁定读取竞争。事务结束会释放行锁；若用独立插入的锁表记录，则还需处理持有者崩溃后的清理。

常见做法是在事务中锁定一条确定存在的业务记录,或利用锁表的唯一键竞争锁;适合已有数据库、竞争不高且临界区较短的场景。

- 事务行锁:BEGIN 后对确定的锁记录 SELECT ... FOR UPDATE,完成受保护操作后提交或回滚;需要合适索引和明确的事务范围。

- 唯一键锁表:插入同一 lock_key 仅允许一个成功;若单独提交锁记录,还需设计持有者、释放权限、超时和故障恢复,否则客户端退出后可能遗留记录。

- 优缺点:能复用数据库事务与唯一约束;竞争会增加数据库负担,长事务占连接和锁,应处理死锁与等待超时。

**易错提醒：** 锁只能保护遵守同一协议的操作,跨外部系统的长任务不能仅凭数据库锁保证全部副作用正确。

**具体场景：** 两个事务对同一条确定存在的锁记录执行 `SELECT ... FOR UPDATE`，后者通常需要等待前者结束事务。若改用独立提交的锁表记录，进程崩溃后还需要过期与恢复协议。

**追问：锁表记录独立提交后客户端崩溃怎么办？** 记录不会随业务进程自动消失，需要持有者标识、超时和恢复协议；而事务行锁与数据库连接和事务生命周期相关，两种方案不可混为一谈。

<span id="79-redis-分布式锁怎样实现-边界是什么"></span>

### 7 Redis 分布式锁怎样实现 边界是什么

**理解与追问：** 随机令牌主要防止误删别人的锁，并不能阻止超时后的旧持有者继续写下游。高正确性场景需让被保护资源校验递增令牌或业务版本，并考虑主从切换造成的锁丢失。

基本做法是使用 SET lock_key 随机令牌 NX PX 租期原子获取锁,解锁时原子校验令牌再删除;令牌用于识别持有者,租期用于故障后释放。

- 获取、设置过期时间必须是一条原子操作;不能先 SETNX 再 EXPIRE。解锁用 Lua 等原子比较后删除,避免删掉其他客户端后来取得的锁。

- 任务可能超过租期,可使用受控续租并在续租失败时停止受保护操作;进程暂停后恢复时,旧持有者仍可能继续执行,续租不能消除这种风险。

- 正确性要求高时,资源端校验单调递增的 fencing token,拒绝旧持有者请求,或用业务版本、唯一约束、条件更新兜底;随机解锁令牌不等于 fencing token。

- 异步复制下主从切换可能丢失尚未复制的锁,产生多个持有者;选型时明确可接受的故障窗口,不能只比较平均吞吐。

**易错提醒：** 加了过期时间或看门狗,不代表在进程暂停、网络分区和故障切换时仍绝对互斥。

**具体场景：** 客户端 A 持锁后暂停，租期到期后 B 获得锁；A 恢复时如果继续写下游，即使用随机值防止误删 B 的锁，也无法阻止旧写入。关键资源需验证 fencing token 或业务版本。

**追问：随机值能防止锁过期后旧任务继续写吗？** 不能。随机值主要用于原子校验后解锁；若旧任务暂停后恢复，仍需资源端校验递增令牌、版本或业务条件。

<span id="80-zookeeper-分布式锁的流程是什么"></span>

### 8 ZooKeeper 分布式锁的流程是什么

**理解与追问：** 等待者只监听前驱节点可以减少惊群，但注册监听时仍要重新检查节点是否存在。会话过期后旧进程可能尚未及时感知，关键写入仍需下游具备拒绝过期持有者的能力。

竞争者在同一锁目录下创建临时顺序节点,序号最小者持锁,其余只监听前驱节点,前驱删除后重新判断是否轮到自己。

- 临时节点与会话绑定,正常解锁删除自己的节点;会话过期后服务器会删除相关临时节点,短暂断线不等于会话立即失效。

- 只监听前驱可减少所有等待者同时唤醒的惊群;注册监听与节点删除之间存在竞争,需要检查节点是否仍存在并循环判断。

- 优点是有序竞争和成熟的会话、通知机制;代价是额外集群及协调通信。客户端失联时应停止受保护操作,但旧进程可能尚不知道会话已过期。

- 下游资源仍应验证 fencing token 或业务条件,拒绝失去锁的旧持有者;重入、公平性和超时等能力取决于客户端实现。

**易错提醒：** ZooKeeper 能一致地管理锁节点,不代表它能强制撤销旧客户端已经发往数据库的写请求。

**具体场景：** 多个客户端创建临时顺序节点，最小序号持锁，其他客户端监听各自前驱。会话过期后节点会被删除，但旧客户端可能延迟感知，因此关键写入仍需资源端保护。

**追问：临时节点消失是否能撤回旧客户端发出的请求？** 不能。客户端可能延迟感知会话过期，已经发出的操作也不会自动撤销；关键资源仍需自己拒绝过期持有者。

<span id="81-dubbo-的服务暴露-引入和调用如何串起来"></span>

### 9 Dubbo 的服务暴露 引入和调用如何串起来

**理解与追问：** 用一次实际调用串联更容易回答：接口代理接收请求，经过过滤、路由和负载选择，再通过协议发送到提供方；响应按请求标识匹配。重试前应评估幂等性和下游超时预算。

服务端把本地实现暴露为可调用的 RPC 服务,消费端发现提供者并建立代理,业务调用代理后经过路由、负载均衡和网络通信到达服务实现。

- 暴露:读取接口、实现与协议等配置,构建服务调用抽象和处理链,启动或复用网络服务,按发现模式发布实例及服务相关信息。

- 引入:通过注册中心发现并订阅提供者变化,或按配置直连;建立调用目标集合、集群容错逻辑和接口代理,地址变化时更新可调用列表。

- 调用:代理进入过滤链,按路由筛选、负载均衡选择目标并编码发送;服务端解码、定位实现并执行,响应通过请求标识关联到调用结果或 Future。

- 治理:超时不代表服务端一定未执行,配置重试前要确认业务幂等;初始化时机、注册粒度、具体扩展实现随版本和配置变化。

**易错提醒：** 不要把某个旧版本的 Spring 事件、源码类名或字节码框架背成所有 Dubbo 版本固定不变的调用流程。

**具体场景：** 消费者调用订单服务接口时，代理先经过过滤和路由，再选提供者并发送请求；超时可能发生在服务端已执行之后。重试扣款类接口前，要先确认幂等策略。

**追问：RPC 超时后重试为什么可能造成重复操作？** 服务端可能已经执行，只是响应未送达。需要结合请求标识、接口幂等、重试次数和总超时预算设计。

<span id="82-常见负载均衡算法如何选择"></span>

### 10 常见负载均衡算法如何选择

**理解与追问：** 实例容量差异大时可考虑权重；请求耗时差异大时，单纯轮询可能分配次数相同但负载不同。哈希路由适合局部性，却可能让热点 key 集中到少量节点。

负载均衡是在候选实例中分配请求,选择时看实例能力、请求耗时差异及是否需要同 key 路由;通常先路由筛选,再做负载选择。

- 随机、轮询及其加权形式:实现直观,用权重反映容量差异;请求耗时差异大时,均匀分配次数仍可能让慢节点积压。

- 最少连接、最少活跃请求、最短响应时间:依据连接数、未完成调用数或响应统计选目标;长连接复用时连接数不能代表实际工作量,统计也有滞后。

- 一致性哈希:相同 key 尽量落到同一节点,扩缩容时减少映射变化,适合缓存亲和;虚拟节点缓解节点分布不均,但不能自动消除业务热点。

- Dubbo 提供加权随机、加权轮询、最少活跃、一致性哈希等策略,具体支持与配置按版本核对;粘滞调用属于保持目标的行为,不能和轮询混成一个标准算法。

**易错提醒：** 负载均衡不能代替限流、熔断和容量规划,也不能承诺每个节点实际负载完全相等。

**具体场景：** 两台服务分别处理 20ms 和 2s 的请求，轮询虽然请求数接近，慢请求所在实例可能积压更多。最少活跃等策略可考虑请求状态，但也有统计滞后，需要结合真实负载。

**追问：轮询平均分配请求为什么负载还可能不均？** 请求耗时和实例容量可能不同。可以比较加权、最少活跃等策略，但它们依赖统计与配置，仍要监控热点和实际延迟。

## 业务设计与稳定性

<span id="90-未支付订单怎样自动取消"></span>

### 11 未支付订单怎样自动取消

**理解与追问：** 订单到期消息只是触发检查：取消前需用订单状态和到期时间做条件更新。支付与取消并发时，只有取得合法状态转换的一方继续；迟到的支付结果还要有明确退款或对账规则。

常用方案是持久化订单到期时间,以延迟任务触发取消,并用定时扫描补偿遗漏。任务到达时重新检查订单状态和到期时间,通过数据库条件更新解决重复触发及支付竞争。

- DelayQueue 适合简单单进程任务,但仅在内存中,重启后需恢复任务,多实例还需协调;take 可阻塞等待到期,不必忙轮询。

- 延迟消息或 Redis 有序集合便于集中调度,但要设计持久性、可靠投递或原子领取、失败重试和重复消费。延迟范围与精度依具体产品配置,不存在通用 24 小时上限。

- 定时扫描依赖到期时间及状态索引,分批处理;精度受扫描周期影响,吞吐与资源占用需要压测。

- 取消应使用类似 status=UNPAID 且 expire_at<=当前时间的条件更新,并根据受影响行数决定后续动作。支付成功与取消共享状态机,晚到支付应明确拒绝或退款规则;跨系统资源释放需可重试和幂等。

**易错提醒：** 收到到期消息不等于订单一定能取消;先读状态再无条件改写存在支付竞争窗口。

**具体场景：** 订单到期消息到达时，支付可能恰好成功。取消操作应按未支付状态和到期时间做条件更新，再依据更新行数决定后续动作；晚到支付结果还要有退款或对账规则。

**追问：支付与自动取消同时发生怎么办？** 两边应基于同一状态机做条件更新，并依据更新结果执行后续动作；对晚到支付还要有明确退款、拒绝或对账规则。

<span id="91-怎样建设系统稳定性"></span>

### 12 怎样建设系统稳定性

**理解与追问：** 从可用性目标和关键用户链路出发，再确定监控、容量、故障隔离和恢复措施。每项方案都应有可验证指标，例如压测吞吐、恢复时间或演练结果，而不是只列组件名。

先确定关键链路和可用性、延迟等目标,再围绕可观测性、容量、依赖故障、变更和恢复设计措施。每项措施都应能通过演练和监控验证。

- 发现问题:监控错误率、延迟、饱和度及业务成功率,配合日志和链路追踪,设置可行动的告警与责任人。

- 承载流量:容量评估与压测、限流和背压、弹性扩容、热点治理、数据库索引与归档。分库分表应由实际容量及运维需求驱动。

- 控制故障传播:明确超时预算、有限重试与退避、熔断和降级、线程及连接资源隔离;重试必须考虑幂等和放大流量。

- 减少变更风险并恢复服务:自动化检查、灰度及回滚、多实例或多故障域部署、备份恢复演练。根据 RTO 和 RPO 选择灾备能力。

**易错提醒：** 多副本不能替代备份,部署多机也不自动保证跨机房容灾;稳定性不能只罗列中间件。

**具体场景：** 针对下单链路先定义成功率和延迟目标，再监控请求、数据库、下游依赖和队列积压。通过压测与故障演练验证限流、降级和恢复是否达到目标，而不是只列出组件名称。

**追问：多机房部署是否等于具备灾备？** 不一定。还要验证故障域隔离、数据复制、切换、备份恢复和 RTO/RPO；通过演练确认关键链路能否达到目标。

<span id="92-新增-接口幂等怎样抵御重复请求与并发"></span>

### 13 接口幂等怎样抵御重复请求与并发

**理解与追问：** 幂等键需要代表同一次业务意图，并与请求参数、处理状态及结果关联。重复键带不同参数应被识别；本地数据库事务以外的支付或第三方副作用还依赖下游幂等和对账。

接口幂等指同一业务操作被重复请求时,业务效果与成功执行一次一致,响应内容不必逐字相同。通常以调用方、操作类型和业务请求号确定唯一操作,并把去重记录与业务变更放在同一本地事务里,让并发请求也只能生效一次。

- 用数据库唯一键仲裁创建操作,记录处理状态和结果;同一幂等键携带不同参数应拒绝,重复请求返回原结果或处理中状态,并约定去重记录保留期。

- 状态流转用带旧状态或版本条件的 UPDATE,按实际变更结果推进;MQ 重投可沿用稳定的业务操作标识,外部接口副作用还需下游支持幂等。

**易错提醒：** 先查询是否存在再执行,或仅在执行前写入 Redis 标记,都不能独自保证业务效果只生效一次。

**具体场景：** 客户端支付请求因超时重试，服务端应根据稳定业务请求号识别同一次操作；若同一幂等键携带不同金额，应识别冲突。外部支付调用也要确认下游的幂等与对账能力。

**追问：重复请求参数不同但幂等键相同怎么办？** 应检测参数冲突并拒绝或按协议处理，不能无条件返回旧结果。去重记录与本地业务变更需有一致的事务边界。

<span id="93-新增-本地事务与-mq-发消息如何保持一致"></span>

### 14 本地事务与 MQ 发消息如何保持一致

**理解与追问：** Outbox 先把业务变更和待发布事件放进同一个本地事务，再由发布器可靠投递。若发送成功后标记失败，事件可能再次发送，因此消费者必须依据稳定事件 ID 或业务键去重。

本地事务与发送 MQ 属于两个资源,先提交哪一个都存在中间失败窗口。Outbox 将业务变更和待发送事件写入同一数据库事务,提交后由独立发布器扫描或通过 CDC 投递消息,使已提交业务最终能发出事件;前提是发布任务可恢复并持续重试。

- 发布器确认 MQ 已接收后再标记已发;若发布成功后、标记前宕机,恢复后会再次投递,因此事件ID 必须稳定,消费者仍需业务幂等。

- 只发布已提交的事件,失败时保留待发送记录并监控重试、积压和告警;同一业务实体要求顺序时,还需序号及发布、消费顺序控制。

**易错提醒：** Outbox 提供可靠最终投递,不能承诺消息永不重复,也不能让外部系统立即完成同一原子事务。

**具体场景：** 订单状态和 outbox 事件写进同一数据库事务；发布器发送成功后若在标记已发送前崩溃，恢复后可能重复发送。因此消费者仍需按事件 ID 或业务操作键去重。

**追问：Outbox 为什么仍会重复发消息？** 发布器可能已获得 Broker 确认，却在标记发送成功前崩溃，恢复后再次投递。消费者要按稳定事件 ID 或业务键实现幂等。

<span id="94-新增-限流-熔断-降级有什么区别-重试为何放大故障"></span>

### 15 限流 熔断 降级有什么区别 重试为何放大故障

**理解与追问：** 限流解决接入量控制，熔断减少对持续故障依赖的调用，降级提供可接受的替代服务。三层各重试三次可能显著放大请求量，应统一超时与重试预算，并检查业务幂等。

限流按速率或并发量限制进入系统的工作,熔断根据下游故障情况暂时阻止调用并探测恢复,降级则减少功能或返回可接受的替代结果,优先保住核心业务。三者可组合使用;重试会增加请求和资源占用,必须限制次数、总时限和重试层级。

- 令牌桶按设定速率补充令牌,容量允许有限突发;漏桶以相对固定速率出队,队列满时拒绝,适合平滑流量;单机额度不等于集群总额度。

- 多层同时重试会乘法放大下游请求;只重试适合重试的故障,确认操作幂等,配合指数退避和随机抖动,尊重限流及熔断信号。

**易错提醒：** 超时不等于下游未执行,降级也不能伪造支付成功等关键业务结果。

**具体场景：** 上游、网关和服务各自多次重试时，一次用户请求可能放大成大量下游调用。对可恢复故障设统一的重试次数与总时限，配合退避、抖动及幂等，避免把故障放大。

**追问：为什么重试会加重故障？** 多层同时重试可能将请求量乘法放大，进一步压垮慢下游。应只重试可恢复故障，统一总时限和层级，结合退避、抖动与幂等约束。
