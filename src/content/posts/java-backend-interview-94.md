## 1 Java 基础与并发

### 1 ArrayList 和 LinkedList 如何选择

ArrayList 基于可扩容数组,按下标访问为 O(1),尾部追加均摊 O(1),中间插入、删除通常要移动元素,为 O(n)。LinkedList 基于双向链表,按下标定位为 O(n);只有已经定位到节点或操作首尾时,链接调整才是 O(1)。选择要结合访问方式和数据规模。

- ArrayList 扩容会分配新数组并复制元素;已知数量时可合理预估容量。

- LinkedList 每个节点还保存前后引用,节点分散;不能只按插入、删除次数判断性能。

- 两者都不保证线程安全;队列、栈场景也应考虑 ArrayDeque。

**易错提醒：** “LinkedList 任意位置插入、删除都是 O(1)”漏算了定位节点的成本。

### 2 如何解决 Hash 冲突 HashMap 怎样处理

不同键可能映射到同一桶。常见处理方法有链地址法、开放定址法、再哈希法等。JDK 8 及后续常见版本的 HashMap 使用数组加链表,并在条件满足时转为红黑树;定位桶后,仍需比较键是否相等,不能只比较哈希值。

- hashCode 相同不代表 equals 相等;equals 相等的对象必须具有相同 hashCode。

- JDK 8 的树化相关常量为阈值 8、最小数组容量 64;数组较小时通常先扩容,不能只背节点数量。

- 作为键使用期间,不应修改参与 hashCode、equals 的字段,否则可能再也定位不到原条目。

**易错提醒：** 扩容能改善桶分布,但不能保证消除所有哈希冲突。

### 3 HashMap 在多线程下会出现哪些问题

HashMap 没有提供并发访问保护。多个线程并发修改时,可能丢失更新、覆盖条目、计数不准确,读线程也缺少可靠的可见性保证。JDK 7 并发扩容中的链表成环是历史问题;JDK 8 改变了实现,仍不能据此认为线程安全。

- 迭代器的 fail-fast 只是尽力发现修改,不能依赖 ConcurrentModificationException 保证正确性。

- 共享只读的 HashMap 也要安全发布;写入场景可用 ConcurrentHashMap 或统一外部加锁。

- ConcurrentHashMap 的单个操作有并发保证,但 get 后再 put 仍是复合操作,应使用 compute、merge 等适合的原子接又。

**易错提醒：** modCount 是修改检测计数,不是同步机制。

### 4 volatile 和 synchronized 分别保证什么

volatile 为变量读写提供可见性和内存顺序保证:对某个 volatile 变量的写,happens-before 后续对它的读。单次 volatile 读写具有原子性,包括 long、double;但 i++ 这种读、改、写复合操作并不原子。synchronized 则通过同一监视器互斥保护临界区,并建立解锁到后续加锁的可见性关系。

- 所有相关访问必须遵守同一同步规则,才能保护业务不变量;两个不同锁不能互相保护。

- volatile 引用不等于对象内部所有字段和操作都自动线程安全。

- synchronized 保证互斥,不表示线程不能被调度、中断请求不能发生,也不表示区内禁止一切重排。

**易错提醒：** 不要笼统地说“volatile 完全不保证原子性”或“synchronized 让线程不能被打断”。

### 5 Condition 与 Object.wait notify 有什么区别

Object 的 wait、notify、notifyAll 与对象监视器配合使用;Condition 的 await、signal、signalAll 与对应 Lock 配合使用。等待会原子地释放关联锁,返回前重新获取锁。一个 Lock 可以创建多个Condition,将不同条件的等待者分组通知。

- 使用 ReentrantLock 的 Condition 时,await 和 signal 都应在持有对应锁时调用,并在 finally 中解锁。

- 条件判断必须使用 while 循环,处理虚假唤醒以及唤醒后条件再次变化。

- signal 选择该条件队列的等待者,不代表可按线程 ID 精确唤醒;被通知后仍需竞争或重新获取锁。

**易错提醒：** notify、signal 不会立即释放当前线程持有的锁。

### 6 sleep yield join interrupt 分别做什么

sleep 暂停当前线程一段时间,不释放它持有的监视器;yield 只是向调度器提示愿意让出执行机会,可能被忽略;t.join() 让调用线程等待 t 终止;interrupt 是协作式中断请求,具体反应取决于线程正在执行什么以及是否检查中断。

- sleep、join、wait 等可中断等待抛出 InterruptedException 时会清除中断标志;无法继续处理时通常应恢复标志或向上传播。

- start 才会启动新线程;直接调用 run 通常只是当前线程执行普通方法。

- await 属于 Condition、CountDownLatch 等工具,不是 Thread 的通用方法。

**易错提醒：** yield 不保证其他线程马上运行;interrupt 也不等于强制杀死线程。

### 7 线程安全的单例有哪些实现

常见实现包括静态成员饿汉式、静态内部类、枚举和双重检查锁。饿汉式与静态内部类利用类初始化机制保证初始化安全;静态内部类还能延迟到使用 Holder 时初始化。双重检查锁要求实例字段为 volatile,并在同步块内再次检查是否为空。

- 双重检查中的 volatile 用于安全发布和必要的内存顺序,避免其他线程观察到未完成初始化的对象。

- 枚举实例具有语言层面对枚举构造和序列化的约束;普通类若参与序列化,还应考虑 readResolve。

- 单例通常只在定义它的类加载器范围内唯一;实例唯一不代表实例中的可变业务状态线程安全。

**易错提醒：** 只在 if(instance == null) 后直接 new,不能保证并发下只创建一次。

### 8 常见线程池与 ThreadPoolExecutor 七个参数是什么

常见工厂方法有固定线程数、单线程、缓存线程池和定时线程池。自定义 ThreadPoolExecutor 的七个参数是 corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、handler。正常接收任务时通常先补足核心线程,再入队;队列不能接收时再扩容到最大线程数,仍不能接收才拒绝。

- newFixedThreadPool、newSingleThreadExecutor 通常使用无界队列,持续过载可能造成任务堆积。

- newCachedThreadPool 使用 SynchronousQueue 直接交接任务,最大线程数很大,持续过载可能造成线程膨胀;定时任务用 ScheduledThreadPoolExecutor。

- keepAliveTime 默认作用于超过核心数量的空闲线程,也可配置核心线程超时;线程工厂可设置业务可识别的名字。

- 队列容量、线程数应结合耗时、阻塞比例、下游容量和压测数据决定,不存在通用最优值。

**易错提醒：** 不存在 new ThreadExcutors“默认线程池”;无界队列下只调大 maximumPoolSize 通常不起作用。

### 9 四种拒绝策略分别怎样处理任务

ThreadPoolExecutor 在关闭后或容量饱和无法接收任务时触发拒绝处理。AbortPolicy 抛出RejectedExecutionException;DiscardPolicy 直接丢弃;DiscardOldestPolicy 在未关闭时移除队头任务并重试;CallerRunsPolicy 在未关闭时让提交任务的调用者线程直接执行。

- CallerRuns 的调用者可能是请求线程、消息消费线程或另一个工作线程,并不固定是 main 线程;线程池关闭后它也会丢弃任务。

- DiscardOldest 丢的是队头,只有 FIFO 队列中才可简单理解为最早入队;重试仍可能失败。

- 任务不能丢时,需要可观测的拒绝反馈、限流或可靠补偿;静默丢弃 FutureTask 可能让 get 长期等待。

**易错提醒：** 拒绝不只在“队列满”时发生,关闭状态也会拒绝新任务。

### 10 线程池有哪些状态 怎样正确关闭

五种状态是 RUNNING、SHUTDOWN、STOP、TIDYING、TERMINATED。RUNNING 接收并处理任务;SHUTDOWN 不接收新任务但处理已入队任务;STOP 不再处理队列任务并尝试中断工作线程;所有任务结束且工作线程数为零后进入 TIDYING,执行终止钩子后进入 TERMINATED。

- shutdown 发起有序关闭;shutdownNow 尝试中断执行中的任务并返回尚未开始的排队任务。

- 关闭方法返回不代表所有任务已经完成,需要 awaitTermination 等方式等待并处理超时。

- 任务不响应中断时,shutdownNow 也不能保证线程池立刻终止;状态转换并不要求依次经过全部五个状态。

**易错提醒：** 最终状态名称是 TERMINATED,不是 TERMINAL。

### 11 AQS 是什么 常见工具怎样使用 state

AQS 是构建锁和同步器的框架,通过原子更新的 state、等待队列及阻塞唤醒机制组织竞争,支持独占和共享模式。state 的业务含义由子类定义,不能把它统一理解成“是否有锁”。队列按先进先出组织,也不意味着所有基于 AQS 的工具自动公平。

- ReentrantLock 用 state 表示重入次数,还要记录拥有者;同一线程可以重入,不是 state 大于零就必须阻塞。

- CountDownLatch 用剩余计数控制等待,减到零后释放等待者;Semaphore 用许可数量控制申请,许可不足才需等待。

- JDK 8/21 的 ReentrantReadWriteLock 将 int state 高 16 位表示读计数,低 16 位表示写重入计数;这是特定版本实现细节。

- JDK 8 的 FutureTask 已不基于 AQS,而是用 CAS 更新状态并维护等待线程栈,不能把旧版实现套到新版本。

**易错提醒：** AQS 字段名是 state,且“释放后唤醒”不等于被唤醒线程必然立即取得资源。

### 12 Java SPI 怎样发现实现

SPI 是服务提供者接又机制:使用方依赖服务接又,提供方按约定声明实现,ServiceLoader 在运行时查找并按需加载提供者,从而降低使用方对具体实现的直接依赖。它提供发现能力,具体选择哪个实现、如何排序仍由使用方或框架决定。

- 类路径方式在 META-INF/services/接又全限定名 文件中逐行写实现类全限定名;对应实现通常需要公开无参构造。

- JDK 9 模块化方式可通过 uses、provides ... with ... 声明服务与提供者。

- 发现过程受类加载器可见性影响;ServiceLoader 实例本身不保证多线程并发使用安全。

**易错提醒：** Dubbo 等框架的 SPI 扩展规则不能直接当成 JDK ServiceLoader 的规则。

### 13 反射和 JavaBeans 内省是什么关系

反射通过 Class 对象及 Method、Field、Constructor 等 API,在运行时检查类型信息并调用成员。Class 是 Java 层的类型表示,不等同于 HotSpot 内部的 InstanceKlass。JavaBeans 的Introspector 在反射等机制上识别 Bean 属性、读写方法和事件,是更高层的内省工具。

- getBeanInfo 返回 BeanInfo,可从 PropertyDescriptor 取得属性名及 getter、setter,适合实现属性映射等功能。

- 访问非公开成员仍受访问控制与模块封装限制;setAccessible 不是在所有 JDK、所有模块上都能成功。

- JDK 9 已移除 rt.jar;JDK 18 核心反射改为基于方法句柄实现,不能把早期内部机制当作长期规范。

**易错提醒：** 反射是否更慢取决于版本、调用方式和优化条件,不能直接背固定性能倍数。

### 14 新增 == equals hashCode 的契约及 String 不可变性

基本类型的 == 比较值,引用类型的 == 比较是否指向同一对象;equals 定义逻辑相等,Object 默认仍比较对象身份。重写 equals 通常必须同时重写 hashCode,使逻辑相等对象具有相同哈希值。String 按内容比较,创建后的字符串内容不能通过正常 API 修改。

- equals 应满足自反、对称、传递和一致性,非空对象与 null 比较应返回 false;参与相等判断的信息未变时,hashCode 应保持一致。哈希相同仍可能是不同对象,不能用哈希值代替相等判断。

- String 不可变依赖禁止被继承、封装内部存储以及不暴露可修改内容等设计,便于共享和用作键。拼接、替换等操作返回结果字符串,原对象不变;变量重新赋值只是改了引用。

**易错提醒：** final 引用不能重新赋值,不代表它引用的任意对象都不可变;字符串内容不要用 == 判断。

### 15 新增 ConcurrentHashMap 如何保证线程安全

JDK 8 的 ConcurrentHashMap 以数组、链表和树组织数据,空桶插入常用 CAS,非空桶更新结合桶级同步,并用必要的可见性机制支持并发读取;扩容时多个线程可协作迁移。它主要提供单键操作的并发保证,不能把一连串业务操作自动变成事务。

- 不要把 JDK 7 的 Segment 分段锁模型直接套到 JDK 8;get 通常不需要获取更新时的桶监视器。键和值均不能为 null,成功读取某键更新后的非空值时,能看到该次更新之前的相关写入。

- 先检查再 put 应按语义改成 putIfAbsent、compute 或 merge 等原子操作;回调宜短小且避免递归修改同一映射。迭代是弱一致的,size 等聚合结果在并发修改期间不能充当精确控制依据。

**易错提醒：** 容器线程安全不等于存入其中的可变对象自动线程安全,也不保证跨多个键的一致性。

### 16 新增 ThreadLocal 原理及线程池中的泄漏风险

ThreadLocal 为当前线程关联一份变量值,JDK 8 中数据实际保存在 Thread 持有的ThreadLocalMap 内,键是 ThreadLocal 的弱引用,值是强引用。线程池工作线程长期存活,任务结束后若未清理,值可能持续被保留,也可能被后续任务错误读到,形成上下文串用。

- 键失去其他强引用后可能被回收,但值不会因此立即回收;后续部分 get、set、remove 路径会清理失效项,不能依赖不确定的清理时机。即使 ThreadLocal 是静态字段,未 remove 的大对象也可能长期占用内存。

- 在任务边界用 try/finally 执行 remove,嵌套上下文则按约定恢复旧值。普通 ThreadLocal 不自动跨线程传递;InheritableThreadLocal 通常在线程创建时继承,不能可靠代表线程池每次提交任务时的上下文。

**易错提醒：** ThreadLocal 只隔离每线程的变量关联;多个线程若存入同一个可变对象,仍会共享该对象。

### 17 新增 CAS 原理 ABA 问题与适用边界

CAS 将内存位置的当前值与预期值比较,相等才原子地写入新值,否则返回失败。调用方可重新读取并计算后重试,形成乐观更新。ABA 指值从 A 变成 B 又变回 A,比较仍成功,却遗漏了中间变化;只有业务依赖变化历史时才构成正确性问题。

- AtomicStampedReference 可把引用和版本戳一起比较更新,前提是修改者遵循版本递增约定;读取引用和版本也应保持配对。版本戳不是自动防错,错误复用或回绕仍需按业务评估。

- CAS 重试在竞争激烈时可能消耗较多 CPU,不能保证每个线程公平或限时成功;重试计算应避免不可重复的外部副作用。多个字段的不变量可封装为不可变状态整体替换,或直接使用适当的锁。

**易错提醒：** 一次 CAS 只提供相应位置的原子更新,不自动保证整个方法、多个独立变量或数据库操作原子。

### 18 新增 死锁的必要条件 预防与定位

典型资源死锁需要同时具备互斥、占有且等待、不可剥夺和循环等待四个条件。例如两个线程分别持有两把锁,并等待对方释放。预防可破坏其中一个条件,工程中常用统一加锁顺序、缩小持锁范围,以及获取失败时释放已持有资源后重试。

- 涉及多资源时可按稳定唯一标识统一排序后加锁;使用 tryLock 超时要配合释放、回滚与退避,避免双方不断互让形成活锁。不要持有业务锁等待不受控的远程调用,也不能把超时本身当作正确释放资源的证明。

- 通过多次线程转储查看持锁者与等待链;ThreadMXBean.findDeadlockedThreads 可检查监视器及可拥有同步器的锁等待环。线程池任务互相等待、外部系统循环依赖等逻辑死锁,不一定能被该接又自动发现。

**易错提醒：** BLOCKED 或 WAITING 状态本身不证明死锁;interrupt 也不能强制解除所有锁等待。

## 2 JVM 与诊断

### 19 JDK 8 为什么用元空间替代永久代

方法区是 JVM 规范中的逻辑区域,永久代和元空间是 HotSpot 在不同版本中的实现方案。JDK 8移除永久代,将类元数据放到本地内存中的元空间,减少永久代容量预估和调优的负担,并改善类元数据的内存管理;这并不意味着方法区消失。

- 元空间不受 Java 堆的 -Xmx 直接限制,但仍受本机或容器可用内存及 MaxMetaspaceSize 等限制,也会发生 OOM。

- MetaspaceSize 主要是触发相关 GC 的初始高水位阈值,不是元空间最大容量。

- 类卸载时可回收对应元数据;类加载器泄漏仍可能导致元空间持续增长。

**易错提醒：** 元空间不是无限内存,也不能简单说成“把整个方法区原样搬到堆外”。

### 20 Tomcat 为什么自定义类加载器

Tomcat 为不同 Web 应用创建独立的类加载器,使各自 WEB-INF/classes 和 WEB-INF/lib 中的类库互相隔离,并通过公共父加载器共享容器类库。重新部署时可创建新的应用类加载器,加载新版本类;JSP 的更新还依赖编译及专用加载流程。

- 应用类默认倾向于先查自身,但 JRE 基础类和 Tomcat 实现的 Servlet、JSP 等 API 有优先委派例外;delegate=true 可调整普通查找顺序。

- 类身份由类名与定义它的类加载器共同确定,同名类未必能互相转换。

- 旧应用的线程、ThreadLocal 或静态引用若仍可达,旧类加载器就可能无法回收。

**易错提醒：** 不能说 Tomcat 对所有类都完全打破双亲委派,或同一加载器可随意重载同名类。

### 21 Java GC 的基本过程怎样回答

先从 GC Roots 出发识别可达对象,再按具体收集器算法回收空间。常见算法有标记清除、复制和标记整理:清除释放垃圾空间,复制或整理会移动存活对象并更新相关引用。不同收集器的阶段、并发方式和停顿点不同,没有所有 GC 都完全相同的固定流程。

- GC Roots 包括活动线程栈中的引用、JVM 内部持有的引用等;循环引用如果整体不可达,也可以回收。

- 并发标记需要处理应用同时修改引用的问题;“并发收集器”也可能包含 Stop-The-World 阶段。

- 对象分配不是所有 GC 最后统一执行的一步;不可达也不保证立刻回收,外部资源应显式关闭。

**易错提醒：** 不是每次 GC 都整理整个堆,也不是所有对象都必须从年轻代进入老年代。

### 22 G1 怎样尽量控制停顿时间

G1 将堆划分为多个 Region,根据历史停顿、存活对象量和回收成本建立预测模型,并调整年轻代规模及混合回收所选的老年代 Region,在目标预算内尽量获得较多可回收空间。MaxGCPauseMillis 是软目标,不能保证每次停顿都不超过它。

- 年轻代回收主要处理年轻代 Region;并发标记后,Mixed GC 在年轻代之外选择部分老年代 Region,并复制存活对象。

- 回收收益不只取决于垃圾比例,还受到存活对象复制、引用扫描等成本影响;不能简单描述为固定优先队列依次回收。

- 目标过紧可能增加回收频率、降低吞吐;内存不足或疏散失败时仍可能出现长停顿甚至 Full GC,应结合 GC 日志判断。

**易错提醒：** G1 既不是完全无停顿,也不是每次暂停都能任意选择少量年轻代 Region。

### 23 怎样排查 Java 进程 CPU 持续过高

先确认是哪个进程、是否持续高占用,再定位热点线程并结合多次线程栈或采样剖析定位代码。Linux 平台线程场景可用 top -H -p PID 找 TID,将十进制 TID 转为十六进制,与线程转储中的 nid对照;同时区分业务计算、忙循环、频繁 GC 和编译等原因。

- 优先使用匹配版本的 jcmd PID Thread.print -l,多次间隔采集;仅一张 RUNNABLE 栈不能证明死循环。

- 结合 JFR、GC 日志、请求量、分配速率确认热点;堆信息可查看 jcmd PID GC.heap_info,并先用help 核对可用命令。

- top 参数及线程 ID 映射依赖系统;虚拟线程不能直接按平台线程的一对一方式套用,应结合支持虚拟线程的转储或 JFR。

**易错提醒：** jmap -heap 不是所有新 JDK 都适用的通用命令;CPU 高也不等于一定是 GC 或死锁。

### 24 新增 JVM 运行时内存区域怎样划分

按 JVM 规范,运行时数据区包括程序计数器、Java 虚拟机栈、本地方法栈、堆和方法区;运行时常量池属于方法区。计数器与栈按线程维护,堆和方法区由线程共享。规范描述逻辑职责,不能把某个 HotSpot 版本的物理布局当成所有 JVM 的强制实现。

- Java 方法调用通常建立栈帧,保存局部变量表、操作数栈和动态链接等信息;局部变量里的引用与其指向对象不是同一块存储。堆用于类实例和数组,方法区保存类型等运行时信息;具体内存位置还受实现和优化影响。

- HotSpot 元空间承载类元数据,但 Java 堆、元空间之外还有线程栈、代码缓存、直接内存和其他本地开销。-Xmx 只限制 Java 堆,不能据此推导整个进程的最大内存;递归过深通常首先关注StackOverflowError。

**易错提醒：** “线程私有”描述访问与生命周期归属,不表示栈帧里引用的对象一定只有该线程能访问。

### 25 新增 类加载过程与双亲委派是什么

类的生命周期包含加载、链接和初始化等阶段;链接又分验证、准备和解析。加载建立类型的运行时表示,验证检查合法性,准备分配类变量等所需存储,解析处理符号引用,初始化执行类变量初始化器及静态代码块。解析可延迟,不必在初始化前全部完成。

- 默认 loadClass 先检查是否已加载,再委托父加载器,父方无法加载时才调用自身 findClass。它按父加载器引用委派,通常不是类继承关系;该机制减少基础类被重复定义和替换的机会,自定义加载器可在规则约束下改变策略。

- 加载不等于初始化:new、调用类的静态方法、读写非常量静态字段等会按规则触发初始化;读取编译期常量通常不会。ClassLoader.loadClass 通常不初始化,而 Class.forName 的单参数形式默认会初始化;应区分类初始化与对象构造。

**易错提醒：** 类加载、类初始化和执行实例构造器是不同动作,不能说“只要引用类名就执行静态代码块”。

### 26 新增 对象创建与内存分配有哪些要点

普通 new 创建对象时,先满足目标类必要的加载、链接和初始化要求,再申请对象存储并使实例字段具有默认值,随后执行相应构造过程。HotSpot 中分配常使用线程本地分配缓冲 TLAB 或受并发保护的共享分配路径;构造器赋值与默认零值初始化要区分。

- TLAB 通常是 Java 堆内划给线程的一块分配区域,用于减少共享分配竞争,不是线程栈;没有TLAB 或空间不足时会走其他路径。分配、回收策略依收集器和参数变化,不能保证所有对象都先进入 Eden 或达到固定年龄才晋升。

- 逃逸分析可帮助 JIT 进行标量替换、消除部分分配和锁,但这依赖编译器实际分析结果,不代表写在方法内的对象就必然分配在栈上。对象从构造器中提前泄露还可能破坏安全发布,不应把引用可见视为构造已完成。

**易错提醒：** 对象的声明位置不直接决定存储位置;引用赋值、内存分配和构造初始化也不是同一动作。

### 27 新增 怎样诊断 OOM 与频繁 Full GC

先按错误明细区分堆空间、元空间、直接内存或本地线程等资源耗尽,再结合进程和容器限制定位。频繁 Full GC 应查看触发原因、耗时及回收前后占用,判断是存活集过大、异常保留、分配压力还是配置问题;它不是内存泄漏的充分证据,也不一定已发生 OOM。

- 堆问题可保留 OOM 堆转储并分析支配树、对象数量及到 GC Roots 的保留路径,结合业务生命周期判断引用是否多余;还要检查缓存、队列、监听器及线程上下文。转储可能暂停应用并占用大量磁盘,应按容量和线上影响安排。

- 回收后占用仍高,需区分合理存活数据与异常保留;占用能明显下降却频繁触发,则检查分配速率、晋升与显式 GC 等原因。本地内存问题还需结合线程数、直接缓冲和已启用的 NMT 等证据,单看堆转储可能找不到全部原因。

**易错提醒：** 调大 -Xmx 可能只是延后故障,还会挤占其他内存;操作系统杀进程也未必产生 Java OOM。

## 3 MySQL 事务 索引与复制

### 28 ACID 分别靠什么保证

原子性表示事务内操作整体提交或回滚,InnoDB 主要利用 undo 撤销修改;一致性表示提交前后满足约束与业务规则;隔离性由 MVCC 与锁共同实现;持久性主要依赖 redo、提交刷盘及可靠存储。四者相互配合,不能把每个字母机械对应到唯一一种日志。

- 一致性既依赖数据库的唯一键、外键、非空约束与事务机制,也依赖正确的业务逻辑。例如转账不能只扣款而不入账,数据库无法自动识别所有业务约束。

- redo 遵循先写日志再刷数据页的思路,脏页可稍后落盘;崩溃后结合 redo 重放、undo 回滚等机制恢复。持久性保证还受日志刷盘配置和磁盘是否真实完成写入影响。

**易错提醒：** 有 redo 不等于任何配置下已提交数据都绝不会丢,隔离性也不是只靠 MVCC。

### 29 四种事务隔离级别和三类读异常是什么

脏读是读到其他事务未提交的数据;不可重复读是在同一事务内重复读同一行时,看到其他事务已提交的修改;幻读是重复执行同一范围条件时,符合条件的行集合发生变化。InnoDB 默认隔离级别为可重复读。

- 读未提交可能脏读;读已提交避免脏读,但可能不可重复读和幻读;可重复读使普通快照读复用一致性快照,并对需要锁定的范围使用相应锁机制;串行化施加更强约束。

- 串行化不等于整个数据库同一时刻只执行一个事务。它让并发执行的效果满足串行执行要求,冲突访问通常需要等待;是否加共享锁还与语句及 autocommit 有关。

**易错提醒：** 讨论 RR 是否有幻读必须先说明是快照读还是当前读,以及是否混用了两者。

### 30 MVCC 快照读 当前读与间隙锁如何配合

MVCC 利用事务信息、undo 版本链和 Read View 判断可见版本。RC 的普通一致性读每条语句建立新快照,RR 通常在第一次一致性读时建立并复用快照。SELECT ... FOR UPDATE / FOR SHARE 及更新删除按当前状态执行,并按需要加锁。

- 记录锁锁住索引记录;间隙锁限制某个索引间隙的插入;临键锁是记录锁加其前方间隙锁。RR 范围锁定读通常用临键锁防止范围内插入,唯一索引完整等值命中已有记录通常只锁该记录。

- RR 快照读不因别的事务新插入而改变原快照,当前读则使用较新状态;事务还能读到自己修改的数据。混用两种读不能假定所有语句看到完全相同的行集合。长事务会拖延旧版本清理。

**易错提醒：** MVCC 解决可见性问题,不能替代写冲突控制;具体锁范围取决于索引、条件和执行计划。

### 31 redo undo binlog 有什么区别

redo 是 InnoDB 用于崩溃恢复的重做日志,描述页等存储结构的修改;undo 保存回滚及构造历史版本所需的信息;binlog 位于 Server 层,以语句或行变更事件等形式记录变化,主要用于复制与基于备份的时间点恢复。

- undo 不能简单说成临时日志:事务提交后,更新 undo 仍可能被其他事务的快照使用,要等不再需要时才清理。redo 循环复用,binlog 通常追加并按保留策略清理。

- 追求较强持久性时通常配置 innodb_flush_log_at_trx_commit=1 与 sync_binlog=1。前者为 0 或 2时存在未刷盘窗又,默认约每秒刷盘也不是严格时限;硬件谎报刷盘仍会破坏保证。

- MySQL 通过内部两阶段提交协调 InnoDB 与 binlog 的提交状态;日志也不能替代完整备份。

**易错提醒：** binlog 不能替代 redo 做 InnoDB 页恢复,undo 也不是提交后立刻消失。

### 32 B 树与 B+ 树有什么区别 为什么适合数据库索引

B 树的内部节点和叶子都可以存放数据记录;B+ 树的内部节点主要保存导航键与子页指针,数据记录集中在叶子,叶子按键有序连接。较高扇出有利于降低树高,按页访问减少磁盘 I/O,叶子链也适合范围查询与顺序扫描。

- InnoDB 聚簇索引叶子保存行数据,二级索引叶子保存索引列及主键值。二级索引不能覆盖查询时,通常还要用主键去聚簇索引取其余列,这称为回表。

- B+ 树所有根到叶子的路径深度一致,但查询耗时仍受缓存命中、扫描行数和回表数量影响。内部导航键重复是结构特点,不应概括成“B 树没有冗余,所以更省空间”。

**易错提醒：** 不是所有索引叶子都存完整行,聚簇索引与二级索引要分开回答。

### 33 为什么常用短小 递增的主键

InnoDB 按聚簇键组织行。递增主键让新记录通常落在索引右端,减少随机插入带来的页分裂与搬移;短主键还能减少每条二级索引记录携带主键的空间成本。自增整数因而是常见选择,但应结合写入并发和分布式生成需求决定。

- 随机且很长的主键可能放大索引、降低缓存效率;业务唯一性仍应由独立的业务唯一键保证,不必把所有业务字段放进主键。

- 递增插入并非永远不分裂,也可能形成右端热点。自增值可能因回滚、失败或并发分配出现空洞,不能依靠连续性推断订单数量,也不能直接当作事务提交顺序。

**易错提醒：** 自增主键是常见性能取舍,不是所有业务都必须采用的规则。

### 34 MySQL 主从复制怎么工作 为什么会延迟

主库产生 binlog,由发送线程向副本提供日志;副本接收线程把事件写入 relay log,应用线程再重放。现代 MySQL 支持协调线程与多个应用工作线程,不应只背“从库固定两个线程”。传统复制默认异步,所以主库提交与副本可读之间存在窗又。

- 延迟可出现在网络传输、接收落盘或应用阶段。大事务、热点更新、锁等待、磁盘或 CPU 不足、查询争用以及事务依赖限制并行度,都可能导致副本追不上。

- 先检查复制线程、错误、GTID 或位点进度与各工作线程状态,再定位慢 SQL、长事务和资源瓶颈。单独看到 Seconds_Behind_Source=0 不能证明某次刚提交的写入已在该副本可见。

**易错提醒：** 提升版本和增加线程只能改善部分瓶颈,不能消除异步复制的本质窗又。

### 35 主从延迟时 如何保证写后读和业务正确性

先明确要求:可接受短暂旧数据的查询可读副本;订单确认等关键写后读可直接回主库。若要在副本上读到指定提交,可传递该提交的 GTID,在选定副本等待执行完成,再以新的事务或快照读取。等待失败时应回主库或明确重试。

- WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout) 返回 0 表示等待成功,1 表示超时。等待完成后不能继续复用等待前已经建立的 RR 快照,否则仍可能看不到目标提交。

- 半同步通常确认副本已接收并记录日志,不等于已应用且查询可见。Redis 或本地缓存能减轻读压力,但缓存本身可能过期,不能自动修复数据库主从一致性。

- 创建、去重、状态流转应依赖主库唯一约束、原子条件更新或事务锁。读副本“未找到”不能作为允许创建的最终依据;等待可见也不能代替幂等控制。

**易错提醒：** 固定睡几百毫秒、检查一次延迟值或加一层缓存,都不能提供确定的写后读保证。

### 36 哪些情况可能不使用预期索引

常见原因有前导通配符 LIKE、索引列上计算或函数、某些隐式类型或字符集转换、联合索引缺少可用前缀,以及优化器判断扫描成本更低。应区分索引不能有效定位、选错索引与成本上主动不用索引,而不是把所有情况统称“索引失效”。

- 普通 B 树通常能用 LIKE 'abc%' 做范围定位,LIKE '%abc' 通常不能。表达式匹配函数索引或生成列索引时可能仍可利用索引;隐式转换是否影响索引也与转换方向有关。

- 联合索引通常遵循最左前缀;WHERE 条件书写顺序不必和索引列顺序一致。范围条件可能限制后续列继续缩小定位区间,但后续列仍可能参与过滤或覆盖。

- NOT IN、<>、低选择性都不是“一定不用索引”;全表扫描也不一定差,应看实际行数、统计信息和执行计划。

**易错提醒：** 不能只凭 SQL 中出现某个关键字就断言索引必然失效。

### 37 如何有依据地优化慢 SQL

先从慢日志或监控确认耗时、调用频率、扫描量与返回量,再看执行计划、实际行数、锁等待和资源压力。围绕过滤、连接、排序与返回列设计合适索引,减少无效扫描和回表,最后在代表性数据与负载下验证收益。

- 只查需要的列,能覆盖时争取覆盖;避免无边界查询和过大事务。批量操作减少往返,但批次过大也会放大锁、日志和复制压力,需要实测。

- UNION ALL 仅在不要求去重时替代 UNION;JOIN、子查询、驱动顺序和 GROUP BY 索引是否更优由语义与计划决定,不能套用“连接一定优于子查询”或“小表永远驱动大表”。

- EXPLAIN ANALYZE 会实际执行查询并报告运行情况,应在可控环境使用。索引有写放大与空间成本,不能为所有字段都建索引。

**易错提醒：** 优化要保持结果语义,不能为了更快而改变去重、排序或事务边界。

### 38 大分页为什么慢 如何优化

LIMIT offset, size 通常要先扫描并丢弃 offset 条记录,偏移越大成本越高。连续翻页可改成基于上页最后排序键的游标分页;必须跳页时,可先用覆盖索引取主键,再取当前页完整行,减少丢弃记录时的回表成本。

- 排序应稳定且唯一,例如按 created_at、id 组合排序,并以二者构造下一页条件;建立匹配过滤与排序的联合索引。仅用非唯一时间字段可能漏行或重复。

- 延迟关联仍要付出扫描大偏移的成本,不是复杂度上的根治。游标分页适合前后连续翻页,但不天然支持任意跳页;并发插入、删除和排序字段变化仍须定义分页一致性规则。SELECT id, created_at, title FROM article WHERE created_at < :lastTime OR (created_at = :lastTime AND id < :lastId)ORDER BY created_at DESC, id DESC LIMIT 20;

**易错提醒：** 把 offset 改为 id > 某值前,要确认主键顺序与业务排序一致。

### 39 新增 InnoDB 死锁如何形成 定位和处理

死锁是多个事务相互持有对方需要的锁,形成循环等待;普通锁等待则未必存在环。InnoDB 通常启用死锁检测并选择一个事务回滚,应用应识别失败并重试整个事务。排查要把等待链、执行语句、索引及事务边界对应起来,不能只调大超时时间。

- 用 SHOW ENGINE INNODB STATUS 看最近死锁,必要时启用 innodb_print_all_deadlocks 留存错误日志;用 performance_schema.data_locks、data_lock_waits 或 sys.innodb_lock_waits 查当前持锁与等待关系,再结合事务持续时间和语句判断阻塞源。

- 治理重点是统一多行、多表加锁顺序,用合适索引缩小扫描与锁范围,保持事务短小,避免持锁访问慢接又。死锁通常回滚整个受害事务;锁等待超时默认通常仅回滚当前语句,应用应明确回滚或重试边界,并给重试设置次数、退避与幂等约束。

**易错提醒：** 即使只改一行,也可能因多个索引、约束检查等产生死锁;加索引或改为 RC 都不能保证永不死锁。

### 40 新增 EXPLAIN 怎么看 覆盖索引 回表和索引下推如何串起来

先看访问方式和实际所选索引,再看预计扫描量、过滤比例及额外操作,判断成本花在扫描、回表还是排序上。覆盖索引让所需列可从索引取得;回表补取其余列;索引下推则先在索引记录上过滤,再决定是否回表,三者解决的问题不同。

- 传统输出关注 type、possible_keys、key、key_len、rows、filtered 和 Extra。possible_keys 是候选,key 才是实际所选;rows 和 filtered 是估算。type=index 可能扫描整个索引,不能只因用了索引就判定高效;结合实际返回量及 ANALYZE 的行数、耗时判断。

- Using index 通常表示覆盖访问;Using index condition 表示 ICP,InnoDB 主要用于需要取完整行的二级索引访问,并不表示无需回表。Using filesort 表示额外排序,不代表一定落盘;Using temporary 表示使用临时表,是否值得优化要看数据规模和实际成本。

**易错提醒：** key_len 不是索引越长越好的评分;覆盖访问也可能因 MVCC 可见性检查需要访问聚簇记录。

## 4 Redis 编码 内存与高可用

### 41 五种常见数据类型的底层编码是什么

逻辑类型与物理编码要分开:String 常见 int、embstr、raw;Hash 小对象常用 listpack,扩大后用哈希表;ZSet 小对象常用 listpack,通用编码由跳表与字典配合;List 使用 quicklist 等编码,而非跳表;Set 可用 intset、哈希表,部分版本也用 listpack。

- Redis 7 起 Hash、ZSet 的紧凑编码重点记 listpack,而非旧教材的 ziplist。List 的 quicklist 连接多个紧凑数据块;较新版本的小 List 也可能直接使用 listpack,应看实际版本。

- 纯整数小 Set 可使用 intset,Redis 7.2 起小 Set 还支持 listpack。切换条件受元素数量、长度和配置影响,不能给所有类型套同一组阈值;可用 OBJECT ENCODING key 查看实例编码。

**易错提醒：** 五种常见类型不是 Redis 的全部类型,编码阈值也不是永不变化的常量。

### 42 压缩列表 listpack 字典和跳表分别解决什么问题

ziplist 和 listpack 都用紧凑连续内存减少小对象的指针开销;字典通过哈希定位提供平均常数级查找;跳表通过多层有序链支持平均 O(log N) 定位和按序遍历。ZSet 用字典查成员分数、跳表维护有序访问,各自承担不同职责。

- 旧 ziplist 的前项长度编码可能导致连锁更新。listpack 改进了元素布局,避免这种前项长度变化的连锁传播;连续内存的插入删除仍可能搬移数据,不等于所有操作都 O(1)。

- 字典需要处理哈希冲突与扩容,Redis 采用渐进式 rehash 思路分摊迁移工作;跳表底层串起全部成员,高层作快速导航。复习优先理解复杂度和用途,不必背容易随版本变化的 C 结构体字段。

**易错提醒：** 跳表不属于 List 的通用实现;紧凑编码省内存也会带来查找和移动成本。

### 43 Redis 如何删除过期键

Redis 结合被动过期与主动过期:访问键时若已到期,就按不存在处理并触发清理;后台还会周期性抽样检查带过期时间的键,主动删除已过期项,避免长期无人访问的过期键一直占用内存。

- 主动扫描受事件循环、工作预算及相关配置影响,不是为每个键创建定时器,也不能承诺固定每 10秒扫一次或固定抽样数量与比例。逻辑到期与物理内存回收时间并不完全相同。

- 过期时间基于时间戳,实例停机不会暂停 TTL。主从复制中,主节点通常集中决定过期删除并传播删除操作;到期通知可能晚于设定时刻,不应把它当成精确可靠的订单到期调度器。

**易错提醒：** 键过期清理与内存不足时淘汰是两套机制,触发条件和可删除对象不同。

### 44 常见八种内存淘汰策略如何分类

Redis 7 的常见八种策略可按候选集合记忆:全部键中选 allkeys-lru、allkeys-lfu、allkeys-random;仅带 TTL 的键中选 volatile-lru、volatile-lfu、volatile-random、volatile-ttl;另有 noeviction。达到 maxmemory 压力时按所选策略处理。

- LRU 偏向淘汰很久未访问的键,LFU 偏向低访问频率,random 随机,volatile-ttl 偏向剩余寿命短的键。Redis 的 LRU/LFU 使用近似机制,不能当成精确维护全部键的全局排序。

- noeviction 不主动淘汰,可能增加内存的命令会报错,普通读取仍可工作;volatile 系列在没有合格候选键时也可能无法腾出空间。maxmemory 应为复制、持久化缓冲与运行开销预留余量。

- “八种”以 Redis 7 常见配置为复习范围,更高版本可能新增策略,应查部署版本。缓存与重要状态混放时,还要评估重要键被淘汰的风险。

**易错提醒：** volatile-ttl 会淘汰尚未到期的键,不能把它称为过期删除策略。

### 45 主从与 Sentinel 有什么区别

基础主从提供数据复制、备份与读扩展,通常写主读从,但它本身不负责完整的自动故障转移。Sentinel 在主从之上增加监控、故障判断、主节点选举切换及服务发现,客户端需要感知新的主节点地址。Sentinel 不负责把一个数据集水平分片。

- 单个 Sentinel 可先判断主观下线,达到配置的 quorum 后形成客观下线判断;真正执行故障转移还需要获得 Sentinel 多数授权,因此 quorum 与选举多数不是一回事。

- 异步复制下,旧主已确认但未复制的写入在切换时可能丢失,读副本也可能读旧值。吞吐上限取决于命令、数据、硬件与网络,不能把某个固定“十万并发”作为架构保证。

**易错提醒：** Sentinel 改善可用性,不自动提供强一致性,也不能突破单主数据集的容量上限。

### 46 Redis Cluster 如何分片 有哪些限制

Redis Cluster 把键空间划为 16384 个哈希槽,一般按 CRC16(key) mod 16384 定位槽,再由槽映射到主节点。扩缩容通过迁移槽及其数据完成;每个主节点可配副本,并由 Cluster 协议处理故障转移。

- 它不是一致性哈希环,也不是 232−1 个虚拟槽。hash tag 可让多个键按同一段 {...} 内容计算槽,便于要求同槽的多键操作,但标签使用不当也可能造成倾斜。

- Cluster 的多键事务和多键脚本通常要求相关键在同槽。节点故障的影响取决于副本、网络分区、槽覆盖和配置,不能承诺“只影响故障节点那部分”;热点键也不会因增加槽自动拆分。

**易错提醒：** Cluster 分片与副本是两个维度,增加副本不会把同一热点键的写压力均匀分散。

### 47 Redis 全量复制与部分重同步如何工作

副本使用 PSYNC 携带复制 ID 与偏移量请求同步;若主节点仍认识该复制历史,且复制积压缓冲保留了所缺区间,就可部分重同步,否则需要全量同步。首次同步一般走全量,但网络断开后不一定每次都重新传整个数据集。

- 全量同步通常由主节点生成并传输 RDB 快照,副本加载后继续处理快照生成期间及之后的增量写入;也支持无盘传输方式。复制 ID 标识数据历史,不能简单等同于进程 runid。

- 复制积压缓冲用于补齐断链期间的缺又,大小可配置,应按写流量和预期断链时间估算;不要把它与副本输出缓冲或全量同步期间的增量缓冲完全混同,也不要写死为 1 MB。

- Redis 默认异步复制。WAIT 可等待一定数量副本确认,降低丢写概率,但不把整个部署变为强一致系统,也不保证所有故障场景下已确认写永不丢失。

**易错提醒：** 部分重同步依赖复制历史匹配与缓冲覆盖,只有偏移量接近还不够。

### 48 新增 RDB AOF 如何取舍 恢复时有哪些持久性边界

RDB 保存某一时刻的数据快照,文件紧凑、适合备份,但崩溃可能丢失上次快照后的写入;AOF记录写操作,持久性取决于刷盘策略,也需要重写控制体积。选型要同时考虑可容忍丢失窗又、恢复时间、磁盘开销和业务是否能从数据库重建。

- 未跳过刷盘且存储可靠时,AOF always 在回复前完成同步刷盘;everysec 通常有约一秒未落盘窗又,实际风险受调度、磁盘及配置影响;no 交由操作系统刷盘。重写期间若配置跳过 fsync,刷盘保证会减弱;复制不能替代本机持久化和独立备份。

- BGSAVE、AOF 后台重写可减少主线程长时间写盘,但 fork 与写时复制仍消耗时间和额外内存。Redis 7 起 AOF 可由基础文件、增量文件及清单组成;同时启用两种持久化时通常优先用 AOF 恢复,应定期验证备份完整性和实际恢复过程。

**易错提醒：** AOF 重写不是把业务历史日志永久保存;不能只备份一个看似最新的文件就认定可完整恢复。

### 49 新增 缓存穿透 击穿 雪崩分别怎么治理

穿透是查询不存在的数据,缓存与数据库均不命中;击穿是某个热点键失效后,大量并发请求一起回源;雪崩是大量键集中失效或缓存服务故障,导致回源流量激增。先识别触发原因,再分别减少无效回源、合并重建请求及限制数据库入又流量。

- 穿透可结合参数校验、短 TTL 空值缓存与布隆过滤器;空值要防止新数据创建后仍被遮蔽。布隆过滤器可能把不存在误判为存在,必须正确维护新增数据,不能因过滤器漏同步就把合法数据永久挡掉;具体能力也取决于部署版本与组件。

- 击穿可用互斥或单飞机制只让少量请求重建,等待者限时等待或按业务允许返回旧值;锁要有到期与持有者校验。雪崩可错开 TTL、提前预热并设置回源并发上限、熔断与降级;整套 Redis 不可用时,TTL 随机化无法提供保护。

**易错提醒：** 逻辑过期返回旧值只适用于容忍陈旧数据的业务,缓存故障时全量放行数据库可能扩大故障。

### 50 新增 缓存与数据库一致性如何设计

常见旁路缓存是读时先查缓存,未命中再读数据库并回填;写时先提交数据库,再删除缓存。这样便于以数据库为事实来源,但两次操作不原子,删除失败、并发回填及副本延迟仍会产生旧值,需要按业务可容忍的陈旧窗又设计补偿和关键读路径。

- 写库成功后进程崩溃可能漏删缓存,可用事务 outbox 或可靠的变更订阅推动失效,并对消费重试、重复、乱序做处理;TTL 作为兜底。若变更事件只存于进程内存,或异步消息没有可靠产生与重试机制,就不能保证最终一定完成失效。

- 即使删缓存成功,先读到旧数据的并发请求仍可能稍后回填;可结合版本校验、受控重建等缩小窗又,回源读副本还要处理复制延迟。跨数据库与缓存的全路径协调成本较高,扣库存、判断唯一性等关键决策应由数据库约束或事务完成,必要时直接读主库。

**易错提醒：** 先写库再删缓存、延时双删、加锁或 CDC 单独使用,都不能自动保证跨存储强一致。

### 51 新增 Pipeline MULTI EXEC WATCH 与 Lua 有什么区别

Pipeline 批量发送命令以减少网络往返,不保证这批命令连续执行;MULTI/EXEC 将排队命令作为一组执行,期间其他客户端命令不会插入;WATCH 在执行前检查关注键是否变化;Lua 把读取、判断、修改放到服务端,适合依赖前一步结果的条件逻辑。

- 事务入队阶段的错误可能使整批不能执行;EXEC 后的运行时错误通常不会撤销已成功命令,也不阻止其余命令继续执行。WATCH 检测到变化会放弃该次执行,应用需重新读并决定是否重试;DISCARD 只是丢弃尚未执行的队列,不是回滚已经发生的修改。

- Lua 执行期间不与其他命令交错,但运行时报错也不会自动撤销此前写入,应先校验参数、类型和业务条件。脚本要短;Pipeline 应分合理批次,避免回复积压。连接超时可能让执行结果不确定,非幂等操作不能盲目整批重放,Cluster 多键操作还需满足同槽要求。

**易错提醒：** Redis 中的执行隔离不等于数据库式失败回滚,也不等于已经可靠刷盘。

### 52 新增 如何识别和治理热 key 大 key

热 key 是访问或资源消耗集中在少数键,大 key 是单键内容或成员过多,两者可以同时存在。先用请求采样、慢日志、内存与网络指标确定具体键和访问模式,再决定降低访问频率、拆分数据还是减少单次返回量,不能只靠增加节点期待自动均摊。

- redis-cli --hotkeys 依赖 LFU 统计,应确认当前策略适用,不要仅为排查随意切换淘汰策略。--bigkeys 偏向按类型找大字符串或成员多的集合,结合 --memkeys、MEMORY USAGE 和业务采样更接近实际内存;扫描要限速,避免直接使用全量 KEYS 或长时间 MONITOR。

- 读热点可用短 TTL 本地缓存、请求合并或预热;写热点只有在业务允许时才能分桶并另行聚合。大集合可按业务边界分片,分页或增量遍历并限制一次取数;删除时评估 UNLINK 等异步释放方式。拆分后仍要维护聚合语义、一致性和失效机制,不能只减少键的大小。

**易错提醒：** 不存在适合所有业务的统一大 key 阈值;UNLINK 也不能消除复制、网络及所有主线程开销。

### 53 新增 Redis 为什么快 单线程边界和阻塞风险是什么

Redis 的常见操作主要在内存完成,专用数据结构降低查找与修改成本,事件循环和 I/O 多路复用高效管理连接,命令执行主路径减少线程竞争。这里的单线程主要指常规命令访问数据的执行模型,并不表示持久化、网络处理和内存释放全部只用一个线程。

- Redis 6 起可用 I/O 线程分担网络读写,后台线程或子进程参与刷盘、异步释放、快照与重写;具体行为依版本和配置。命令执行仍可能受单核、网络或内存带宽限制,多实例、Cluster 可以分散多个键的负载,但不会自动拆分单个热点写键。

- KEYS、大范围集合运算、巨大返回、长 Lua 脚本以及同步释放大对象等可能占用执行主线程,拖慢其他客户端;应控制复杂度与批量大小,用 SCAN 等增量方案。BLPOP 等阻塞式等待通常挂起的是当前客户端,不会在等待元素期间卡住整个服务,要与慢命令区分。

**易错提醒：** 内存数据库也会受缺页、swap、fork 和磁盘刷盘影响;低平均延迟不能证明没有尾延迟风险。

## 5 Spring 与 MyBatis

### 54 Spring MVC 的请求处理流程

请求先进入 DispatcherServlet,由 HandlerMapping 找到处理器及拦截器链,再由 HandlerAdapter调用 Controller。返回结果如何输出,取决于控制器方法的返回类型和注解。

- 视图场景:返回 ModelAndView 或视图名,经 ViewResolver 找到 View,再渲染响应。

- 接又场景:@ResponseBody 或 @RestController 的返回值通常由 HttpMessageConverter 序列化为 JSON 等响应体。

- 异常可交给 HandlerExceptionResolver 体系处理,例如 @ExceptionHandler。

**易错提醒：** 不是所有请求都经过视图解析和页面渲染;REST 接又一般直接写响应体。

### 55 七种事务传播行为与实现原理

传播行为定义:一个带事务的方法调用另一个带事务的方法时,如何使用已有事务。先区分加入同一个物理事务、创建独立事务,以及在同一事务内建立保存点。传播行为 已有事务 没有事务REQUIRED 默认 加入当前事务 创建事务REQUIRES_NEW 挂起外层并创建独立事务 创建事务NESTED 同一物理事务内创建保存点 按 REQUIRED 创建事务SUPPORTS 加入当前事务 非事务执行NOT_SUPPORTED 挂起当前事务后非事务执行 非事务执行MANDATORY 加入当前事务 抛异常NEVER 抛异常 非事务执行

- 常规命令式事务由代理拦截器调用事务管理器;连接等资源通常绑定到当前线程。普通新线程不会自动继承该事务。

- REQUIRED 的内部逻辑事务若标记 rollback-only,外层即使捕获异常,最终仍可能无法提交并抛UnexpectedRollbackException。

- REQUIRES_NEW 独立提交或回滚,外层资源暂挂;需留意连接池额外占用及锁等待。NESTED 常依赖 JDBC 保存点和事务管理器支持,外层回滚仍会撤销内层修改。

**易错提醒：** REQUIRED 不是独立子事务;NESTED 不是 REQUIRES_NEW;挂起能力和保存点能力取决于事务管理器。

### 56 事务未生效或没有回滚时怎样排查

按代理入又、事务基础设施、异常规则、资源与线程边界依次排查。先确认调用确实经过 Spring 管理的代理,再检查实际事务是否开启以及回滚条件是否满足。

- 常见原因:手动 new 对象、未启用事务支持、类内 this 调用绕过代理、选错事务管理器,或者数据源和操作资源不匹配。

- 默认规则是 RuntimeException 和 Error 回滚,受检异常默认不回滚;可按业务设置 rollbackFor。异常被吞掉且未标记回滚时,代理通常看不到失败。

- JDK 接又代理要求事务方法是接又公开方法;Spring 6 起,类代理默认也支持受保护及包可见方法。private 方法和类代理中的 final 方法不能被相应代理增强。

- 异步线程、非事务存储引擎,以及非事务传播配置,都可能使实际行为不符合预期。

**易错提醒：** public 不是事务失效原因;也不能把非 public 一概判为所有 Spring 版本都无效。

### 57 JDK 动态代理与 CGLIB 的区别

JDK 动态代理生成实现接又的代理对象,调用通过 InvocationHandler 分发;CGLIB 生成目标类的子类,以方法拦截实现增强。选型主要看接又、可继承性及框架配置。

- JDK 代理可通过接又代理 final 类的接又方法;CGLIB 不能继承 final 类,也不能覆盖 final 或private 方法。

- Spring AOP 的两种代理都有自调用绕过增强的问题。优先把需要代理调用的方法拆到协作 Bean;也可在理解依赖关系后通过代理引用调用。

- Spring Framework 的接又代理偏好和 Spring Boot 的默认配置不能混为一谈,实际使用哪一种应查看配置和代理类型。

**易错提醒：** 代理性能随版本、调用路径和测试条件变化,不应背固定优劣和百分比。

### 58 循环依赖与三级缓存的边界

Spring 在允许循环引用时,可通过提前暴露 Bean 引用,解决一部分单例属性注入循环依赖。构造器形成的完整闭环通常在实例尚未创建时就互相等待,无法按这一机制处理。

- 一级缓存 singletonObjects 保存完成创建的单例;二级 earlySingletonObjects 保存早期引用;三级singletonFactories 保存产生早期引用的工厂。

- 典型流程:A 实例化后放入早期引用工厂;A 注入 B;B 创建并依赖 A 时取到 A 的早期引用;B 完成后回填 A,最终 A 完成创建。早期引用可能需要与 AOP 代理协调。

- prototype Bean 的循环依赖不能依赖这套单例缓存处理。部分依赖可用 @Lazy 或 ObjectProvider延迟解析,但前提是不要在构造过程中立即解引用。

- Spring Boot 2.6 起默认禁止循环引用;更稳妥的设计是拆解双向依赖和重新划分职责。

**易错提醒：** 三级缓存不是对所有循环依赖都有效,@Lazy 也不是任意构造器循环的通用修复。

### 59 Spring 与 Spring MVC 的父子容器

传统 Servlet 应用可以用根容器放共享业务和持久层 Bean,用 DispatcherServlet 子容器放控制器等 Web 配置。子容器能查找父容器 Bean,父容器不能反向查找子容器 Bean。

- 这样能隔离多个 Servlet 的 Web 配置,并共享服务和数据访问组件。

- 容器边界有助于分层,但不等于 Java 编译器禁止 Service 引用 Controller。现代 Spring Boot 应用也不一定使用这一父子结构。

**易错提醒：** 父子容器是一种应用配置方式,不是所有 Spring MVC 应用的必备结构。

### 60 MyBatis 怎样记录执行耗时

可实现 Interceptor,在 invocation.proceed 前记录 System.nanoTime,并在 finally 中记录耗时。拦截层次应与想测量的范围一致。

- MyBatis 提供 Executor、StatementHandler、ParameterHandler、ResultSetHandler 四类插件拦截点。

- 拦截 Executor.query 或 update,可记录映射语句执行链路耗时,可能包含缓存命中和结果映射;需要贴近 JDBC 执行时,可选择 StatementHandler 的 query 或 update 等方法。

- 批量更新可能到 flushStatements 才真正发送;应用侧耗时也不等于数据库服务端纯执行时间,应结合数据库慢日志判断。记录语句标识,按阈值采样并脱敏参数。

**易错提醒：** 仅有一条 SQL 日志不能说明数据库用了多久;不要把完整参数无差别写入日志。

### 61 新增 IoC DI 与 Bean 生命周期怎样串起来

IoC 把对象创建及依赖管理交给容器,DI 是容器注入依赖的方式。典型 Bean 从定义注册开始,经历实例化、依赖注入、初始化及后处理,必要时包装成代理,最后对外提供服务;容器关闭时执行受管理 Bean 的销毁逻辑。

- 初始化阶段关注 @PostConstruct、InitializingBean.afterPropertiesSet、配置的 init 方法。@PostConstruct 由后处理器触发,不能把它简单当成构造器的一部分;此时不要假定对自身的调用已获得 AOP 增强。

- BeanFactoryPostProcessor 修改 Bean 定义等容器元数据,BeanPostProcessor 处理 Bean 实例及初始化前后逻辑。prototype Bean 创建后通常不由容器自动执行销毁回调,资源需自行管理。

**易错提醒：** 实例化不等于依赖注入和初始化都已完成;容器生命周期也不能替代外部资源的可靠清理。

### 62 新增 Spring 单例 Bean 为什么不一定线程安全

Spring 的 singleton 表示同一容器内同一 Bean 定义通常共享一个实例,并不自动给方法加锁。多个请求同时操作该实例中的可变字段,仍可能发生覆盖、竞态和可见性问题。线程安全取决于状态与访问方式。

- 业务 Service 通常尽量无状态,把请求数据放方法局部变量或明确的请求上下文;局部变量引用了共享对象时,对该对象的操作仍需保护。

- 确需共享状态时,使用不可变对象、合适的并发容器、原子操作或统一加锁;多实例部署的业务唯一性和状态流转还需数据库等共享资源保证。

**易错提醒：** @Service、@Component、@Transactional 和 singleton 本身都不是共享可变字段的线程安全声明。

### 63 新增 Spring AOP 怎样工作 常见通知有什么区别

Spring AOP 在符合切点的方法调用外建立代理拦截链,将日志、事务等横切逻辑与业务代码分开。调用进入代理后,按配置执行通知并推进到目标方法,再沿调用链返回;异常也会影响后续通知路径。

- Before 在目标调用前执行;AfterReturning 针对正常返回;AfterThrowing 针对匹配异常;After 具有 finally 语义。Around 可通过 proceed 决定是否及何时继续调用,并处理返回值和异常。

- 多切面的嵌套由优先级等规则控制,进入与退出方向相反。Spring 代理 AOP 主要面向方法执行,和可支持更多连接点的 AspectJ 织入机制有区别。

**易错提醒：** 不能把所有通知背成一条不分正常与异常的固定顺序;Around 吞掉异常还可能改变事务回滚行为。

### 64 新增 Spring Boot 自动配置与 starter 是什么关系

starter 主要聚合某类功能所需依赖;自动配置则根据类路径、属性、已有 Bean 等条件,决定注册哪些配置与组件。@SpringBootApplication 组合配置声明、自动配置启用及组件扫描等能力。引入依赖并不意味着所有配置都会无条件生效。

- 自动配置先发现候选配置,再用 @ConditionalOnClass、@ConditionalOnMissingBean 等条件筛选;用户自定义组件常能使相应默认配置退让。排查时查看条件评估报告及实际 Bean。

- 现代 Boot 使用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 声明自动配置候选,旧版本常见 spring.factories。组件扫描与自动配置导入是不同入又。

**易错提醒：** starter 不等于自动配置代码本身,也不能把某一版本的候选配置文件当作所有版本的固定实现。

### 65 新增 MyBatis 参数绑定与字符串替换有什么区别

#{} 通常将值映射为 PreparedStatement 的参数占位符,并通过 JDBC 绑定值;${} 则把内容直接拼入 SQL 文本。普通业务值应优先用参数绑定,避免用户输入被当作 SQL 结构执行。两者区别在于参数化与文本替换,不只是是否自动添加引号。

- 表名、列名、排序方向等 SQL 结构通常不能作为值参数绑定;确需动态选择时,由服务端枚举或白名单映射到可信 SQL 片段,不能把请求参数直接塞入 ${}。

- IN 条件的多个值可通过 foreach 生成多个绑定占位符。参数化能防止绑定值改变 SQL 结构,但不会自动修复其他位置的拼接、越权查询或错误业务条件。

**易错提醒：** 用了 MyBatis 不等于天然没有 SQL 注入风险;#{} 也不能直接替代动态表名或列名。

## 6 消息队列与 Kafka

### 66 MQ 有什么作用 代价是什么

MQ 的主要作用是异步、解耦和削峰:把非必要的同步工作交给消费者处理,让生产者和消费者独立扩缩容,并用队列暂存突发流量。

- 异步:如下单后发送通知,主链路只等待必要步骤完成;需要区分“消息已接收”和“业务已完成”。

- 解耦:生产者发布业务事件,不必直接依赖每个下游服务;事件格式仍需版本管理。

- 削峰:按下游承受能力消费,不能凭空增加处理能力;积压量、消费延迟、保留时间和故障补偿都要监控。

**易错提醒：** 引入 MQ 会带来重复、乱序、积压及最终一致性问题,不能只背三个优点。

### 67 Kafka 为什么能够实现高吞吐

核心是把大量小请求合并成批量的顺序日志读写,再利用操作系统页缓存、压缩和分区并行,减少磁盘随机访问、网络往返和数据复制。

- 日志追加写:按分区顺序追加;常用数据由页缓存加速,减少直接依赖随机磁盘 I/O。

- 批量与压缩:生产者聚合记录,消费者批量拉取;批次压缩降低传输和存储开销,但批量等待会增加延迟。

- 高效传输与并行:适用路径利用 sendfile 等机制减少用户态与内核态复制;不同分区可分散到不同Broker 并行处理,TLS 等场景会改变传输路径。

**易错提醒：** 不能把“磁盘顺序写一定快于内存随机写”或“所有读写都经过 mmap、零拷贝”当作通用结论。

### 68 Kafka 如何降低消息丢失风险

按生产、存储、消费三段保证:确认发送结果并可靠补偿,配置副本和确认条件,业务处理成功后再推进消费位点;可靠性必须明确故障范围。

- 生产端:检查 Future 或回调,启用幂等生产;对可重试故障设置退避与 delivery.timeout.ms 总时限,最终失败进入可恢复的补偿流程;业务落库和发消息之间可用事务 outbox。

- 存储端:例如副本因子为 3、min.insync.replicas=2、acks=all;all 等待当前 ISR 中的全部副本,最小 ISR 限制可接受写入的副本数量,不代表只等两个,也不代表全部分配副本。

- 故障切换:避免让缺少已确认记录的副本被不安全选举为 Leader;副本跨故障域部署。

- 消费端:业务成功后提交连续完成位置的下一条 offset;失败重试并做好业务幂等,监控提交失败、积压和数据过期。

**易错提醒：** 无限重试、手动提交或 acks=all 单独使用,都不能承诺任何故障下绝不丢消息。

### 69 Kafka 如何保证业务消息的顺序

Kafka 只保证单个分区的日志顺序;要保证同一订单的处理顺序,必须让该订单进入同一分区,并在生产和消费两侧保持业务顺序。

- 生产端:使用订单 ID 等稳定 key 分区;多个生产者同时发送时,Broker 追加顺序未必等于业务先后,必要时增加业务序号。

- 重试:启用幂等并满足客户端配置约束;关闭幂等且允许多个请求在途时,失败批次重试可能导致乱序。

- 消费端:同一分区或同一 key 串行处理;异步多线程不能越过未完成记录提交 offset,扩分区导致key 映射变化时也需迁移方案。

**易错提醒：** 同一分区日志有序不等于多线程业务执行有序,更不等于整个 Topic 全局有序。

### 70 至多一次 至少一次 恰好一次怎么区分

三种语义描述失败重试时的结果:至多一次允许遗漏、避免重投;至少一次允许重复、要求可靠重试;恰好一次要求在明确的事务边界内,业务结果只生效一次。

- 至多一次:先提交 offset 再处理,提交后宕机会跳过未处理消息;生产端不确认、不补发也可能丢失。

- 至少一次:先成功处理再提交 offset,处理成功但提交前宕机会重放;消费者必须用业务唯一键、去重记录或条件更新消除重复副作用。

- 恰好一次:Kafka 读→处理→写回 Kafka,可把输出记录和输入 offset 放入同一事务,并让下游读已提交数据;写外部数据库则需额外协调业务结果与消费进度,例如同一数据库事务内去重。

**易错提醒：** 自动提交开关本身不能定义投递语义,单独保存 offset 或调用 seek 也不能实现端到端恰好一次。

### 71 Kafka 事务消息的核心流程是什么

Kafka 事务把跨分区写入作为一个提交或中止的整体;用于消费后再生产时,还可以把消费组offset 纳入同一事务,构成 Kafka 范围内的原子处理。

- 生产者配置稳定且不与其他活跃实例冲突的 transactional.id,初始化事务后获取生产者身份和epoch;新的合法实例可隔离旧实例,重启并不表示继续执行原来未完成的事务。

- 业务流程:beginTransaction → 发送记录 → 必要时 sendOffsetsToTransaction →commitTransaction;可中止异常走 abortTransaction,并按异常类型决定重试或终止。

- 事务协调器把状态持久化到 __transaction_state,并驱动相关分区写入 commit/abort marker;下游isolation.level=read_committed 时过滤中止事务,并等待未决事务的可见性边界。

**易错提醒：** Kafka 事务不会自动把 MySQL 写入或第三方接又调用一起提交,事务状态主题分区数也不是固定业务常量。

### 72 Kafka 为什么移除 ZooKeeper KRaft 做了什么

KRaft 把集群元数据管理收回 Kafka,由 Controller 仲裁组通过 Raft 复制元数据日志,减少对独立ZooKeeper 集群的依赖并统一控制面。

- Controller 负责 Broker 注册、分区与副本元数据等管理,Broker 主要处理业务数据;控制面与数据面承担不同职责。

- 元数据日志及快照用于传播和恢复集群状态,控制器多数派选举活跃 Controller;运维仍需规划仲裁成员、故障域及恢复流程。

- 消费者 offset 在现代 Kafka 中存于内部主题 __consumer_offsets,不能笼统说一直由 ZooKeeper保存;业务分区副本复制也不能直接等同于 Controller 的 Raft 元数据复制。

**易错提醒：** 移除 ZooKeeper 是架构演进,不能归因为“ZooKeeper 属于 CP,所以性能一定差”。

## 7 分布式事务

### 73 2PC 是什么 有哪些主要问题

两阶段提交由协调者统一决定多个参与者提交或回滚:先准备并收集投票,再持久化全局决议并通知各参与者完成。

- 准备阶段:参与者执行本地事务、持久化可恢复的准备状态并保留必要资源;返回 Yes 表示承诺之后能按决议完成。

- 决议阶段:所有参与者同意才决定提交,否则在尚未决定提交时决定回滚;决议必须可恢复,通知失败应按既定决议继续恢复和重试。

- 主要代价:多轮通信、日志和锁持有时间;已准备的参与者若无法获知决议,可能阻塞,需要协调者恢复、查询及运维处理。

**易错提醒：** 未收到提交通知可能暂时停留在准备态,规范恢复流程不是让它擅自回滚而造成永久分歧。

### 74 3PC 与 2PC 有什么区别

3PC 通常分为 CanCommit、PreCommit、DoCommit,在投票与最终提交之间增加预提交状态,使节点在特定故障假设下更容易判断后续动作。

- CanCommit 询问是否可提交;PreCommit 推进参与者进入预提交状态;DoCommit 根据协议完成不可逆的最终提交。

- 额外状态和通信轮次可以减少部分协调者故障造成的阻塞,但其非阻塞性质依赖网络及时性、故障检测等假设,不能外推到任意异步网络。

- 网络分区或无界延迟下,超时无法可靠区分节点宕机和消息延迟;简单“超时就提交或回滚”不能同时保证原子性与可用性。

**易错提醒：** 提交决议已经确定或参与者已经提交后,协调者不能因为 Ack 超时再发 abort 推翻提交。

### 75 TCC 是什么 适用于什么场景

TCC 将业务拆成 Try、Confirm、Cancel 三个操作:先检查并预留资源,再由全局结果决定确认使用资源或释放预留,是业务层面的两阶段事务方案。

- Try:校验并冻结库存、额度等业务资源,预留动作应在本地事务内完成;预留后的资源不能再被其他事务使用。

- Confirm:把已预留资源转成正式结果;Cancel:释放预留资源,二者都要支持重复调用且相互排斥。

- 适合能够清晰定义预留、确认、取消语义的业务;相比长时间持有数据库事务锁,TCC 转为维护业务冻结状态,但开发、补偿和异常恢复成本更高。

**易错提醒：** TCC 不要求所有阶段共用一个数据库事务,也不能把不可逆的外部操作随意放进 Try。

### 76 TCC 如何处理幂等 空回滚和悬挂

用全局事务 ID 与分支 ID 唯一标识分支,通过持久化状态机、唯一约束和本地事务约束状态转换,确保重复与乱序请求不会重复改变业务资源。

- 幂等:Confirm、Cancel 的应答丢失会触发重试;检查已确认、已取消状态,重复请求返回原结果,不能重复扣减或释放。

- 空回滚:Cancel 到达时 Try 尚未执行或未成功,不应释放不存在的冻结资源;仍需记录已取消或防悬挂标记。

- 悬挂:Cancel 先完成,延迟的 Try 后到;Try 必须检查取消标记并拒绝预留,否则会遗留无法确认或释放的资源。

- 原子性:状态表与冻结、扣减、释放等业务变更放在同一本地事务内,并用锁或条件更新处理并发,不能仅在内存里“先查再改”。

**易错提醒：** 空回滚直接返回成功但不留取消记录,只解决了当次回滚,仍可能发生后到 Try 悬挂。

### 77 新增 CAP 与 BASE 如何用于系统选型

CAP 指出,网络分区发生时,系统不能同时保证线性一致性和每个非故障节点都能成功响应请求。选型应按具体操作判断:资金扣减优先守住一致性,展示数据可容忍短暂旧值。BASE 强调基本可用、软状态、最终一致,需要明确收敛、补偿及冲突处理机制。

- CAP 的一致性指操作看起来按实时顺序发生在单一副本上,不等于数据库 ACID 中的约束一致性;可用性也不等于通常的年度可用率。

- 分区时可拒绝部分请求以保一致,或接受可能冲突的操作再修复;局部事务仍可使用 ACID,跨服务数据再通过可靠事件逐步收敛。

**易错提醒：** CAP 不是任意“三选二”,BASE 也不是放任数据不一致后自动恢复的保证。

## 8 分布式锁与 RPC

### 78 如何用 MySQL 实现分布式锁

常见做法是在事务中锁定一条确定存在的业务记录,或利用锁表的唯一键竞争锁;适合已有数据库、竞争不高且临界区较短的场景。

- 事务行锁:BEGIN 后对确定的锁记录 SELECT ... FOR UPDATE,完成受保护操作后提交或回滚;需要合适索引和明确的事务范围。

- 唯一键锁表:插入同一 lock_key 仅允许一个成功;若单独提交锁记录,还需设计持有者、释放权限、超时和故障恢复,否则客户端退出后可能遗留记录。

- 优缺点:能复用数据库事务与唯一约束;竞争会增加数据库负担,长事务占连接和锁,应处理死锁与等待超时。

**易错提醒：** 锁只能保护遵守同一协议的操作,跨外部系统的长任务不能仅凭数据库锁保证全部副作用正确。

### 79 Redis 分布式锁怎样实现 边界是什么

基本做法是使用 SET lock_key 随机令牌 NX PX 租期原子获取锁,解锁时原子校验令牌再删除;令牌用于识别持有者,租期用于故障后释放。

- 获取、设置过期时间必须是一条原子操作;不能先 SETNX 再 EXPIRE。解锁用 Lua 等原子比较后删除,避免删掉其他客户端后来取得的锁。

- 任务可能超过租期,可使用受控续租并在续租失败时停止受保护操作;进程暂停后恢复时,旧持有者仍可能继续执行,续租不能消除这种风险。

- 正确性要求高时,资源端校验单调递增的 fencing token,拒绝旧持有者请求,或用业务版本、唯一约束、条件更新兜底;随机解锁令牌不等于 fencing token。

- 异步复制下主从切换可能丢失尚未复制的锁,产生多个持有者;选型时明确可接受的故障窗又,不能只比较平均吞吐。

**易错提醒：** 加了过期时间或看门狗,不代表在进程暂停、网络分区和故障切换时仍绝对互斥。

### 80 ZooKeeper 分布式锁的流程是什么

竞争者在同一锁目录下创建临时顺序节点,序号最小者持锁,其余只监听前驱节点,前驱删除后重新判断是否轮到自己。

- 临时节点与会话绑定,正常解锁删除自己的节点;会话过期后服务器会删除相关临时节点,短暂断线不等于会话立即失效。

- 只监听前驱可减少所有等待者同时唤醒的惊群;注册监听与节点删除之间存在竞争,需要检查节点是否仍存在并循环判断。

- 优点是有序竞争和成熟的会话、通知机制;代价是额外集群及协调通信。客户端失联时应停止受保护操作,但旧进程可能尚不知道会话已过期。

- 下游资源仍应验证 fencing token 或业务条件,拒绝失去锁的旧持有者;重入、公平性和超时等能力取决于客户端实现。

**易错提醒：** ZooKeeper 能一致地管理锁节点,不代表它能强制撤销旧客户端已经发往数据库的写请求。

### 81 Dubbo 的服务暴露 引入和调用如何串起来

服务端把本地实现暴露为可调用的 RPC 服务,消费端发现提供者并建立代理,业务调用代理后经过路由、负载均衡和网络通信到达服务实现。

- 暴露:读取接又、实现与协议等配置,构建服务调用抽象和处理链,启动或复用网络服务,按发现模式发布实例及服务相关信息。

- 引入:通过注册中心发现并订阅提供者变化,或按配置直连;建立调用目标集合、集群容错逻辑和接又代理,地址变化时更新可调用列表。

- 调用:代理进入过滤链,按路由筛选、负载均衡选择目标并编码发送;服务端解码、定位实现并执行,响应通过请求标识关联到调用结果或 Future。

- 治理:超时不代表服务端一定未执行,配置重试前要确认业务幂等;初始化时机、注册粒度、具体扩展实现随版本和配置变化。

**易错提醒：** 不要把某个旧版本的 Spring 事件、源码类名或字节码框架背成所有 Dubbo 版本固定不变的调用流程。

### 82 常见负载均衡算法如何选择

负载均衡是在候选实例中分配请求,选择时看实例能力、请求耗时差异及是否需要同 key 路由;通常先路由筛选,再做负载选择。

- 随机、轮询及其加权形式:实现直观,用权重反映容量差异;请求耗时差异大时,均匀分配次数仍可能让慢节点积压。

- 最少连接、最少活跃请求、最短响应时间:依据连接数、未完成调用数或响应统计选目标;长连接复用时连接数不能代表实际工作量,统计也有滞后。

- 一致性哈希:相同 key 尽量落到同一节点,扩缩容时减少映射变化,适合缓存亲和;虚拟节点缓解节点分布不均,但不能自动消除业务热点。

- Dubbo 提供加权随机、加权轮询、最少活跃、一致性哈希等策略,具体支持与配置按版本核对;粘滞调用属于保持目标的行为,不能和轮询混成一个标准算法。

**易错提醒：** 负载均衡不能代替限流、熔断和容量规划,也不能承诺每个节点实际负载完全相等。

## 9 网络与身份认证

### 83 HTTPS 怎样保证传输安全

HTTPS 是 HTTP 通过 TLS 传输。TLS 通过证书验证对端身份,通过握手协商会话密钥,再用对称认证加密保护应用数据的机密性和完整性。

- 证书把主体身份与公钥绑定,CA 对证书内容签名。客户端验证证书链、域名、有效期等,并验证服务端确实持有相应私钥。签名验证应表述为验签,不能泛化为用公钥解密。

- 现代 TLS 常使用临时 ECDHE 等密钥协商,双方推导密钥;TLS 1.3 不再采用旧式 RSA 密钥传输。应用数据通常使用 AES-GCM 或 ChaCha20-Poly1305 等算法。

**易错提醒：** 对称密钥不必明文传输;公私钥不能笼统说成可以互相加解密;HTTPS 不保证业务端点自身安全。

### 84 HTTP 各版本的主要变化

主要演进方向是连接复用、并发传输和减少队头阻塞。HTTP 版本本身不等于是否加密,实际传输还需看 TLS 和协议使用方式。

| 版本 | 关键特征 | 复习重点 |
| --- | --- | --- |
| HTTP 1.0 | 文本报文，通常每次请求新建连接 | 可有持久连接扩展，不宜绝对化 |
| HTTP 1.1 | 默认持久连接，支持管线化 | 管线化响应需按序返回，存在 HTTP 层队头阻塞 |
| HTTP 2 | 二进制帧、多流复用、HPACK | 共享 TCP，丢包仍可能阻塞连接上的多个流 |
| HTTP 3 | 基于 QUIC、QPACK，集成 TLS | QUIC 基于 UDP，流间通常不因单流丢包而相互等待 |

- QUIC 提供可靠传输、流控和拥塞控制;连接 ID 支持在条件满足时迁移连接。HTTP 2 曾支持服务端推送,但不能据此推断所有客户端仍支持。

**易错提醒：** 二进制帧不等于整体数据必然更少;HTTP 3 也没有消除所有应用和拥塞层面的等待。

### 85 TCP 为什么三次握手和通常四次挥手

三次握手让双方交换并确认初始序列号,建立双向连接状态,并减少旧连接报文造成的误建立。关闭时两个方向分别结束,因此通常需要四个报文段。

- 握手:SYN seq=x → SYN ACK seq=y ack=x+1 → ACK ack=y+1。SYN 会消耗一个序列号。

- 关闭:主动方 FIN → 对方 ACK → 对方准备完毕后 FIN → 主动方 ACK。FIN 表示该方向不再发送数据,并不代表另一方向立即关闭。

- ACK 与 FIN 有时可以合并,因此不是每次抓包都恰好四个报文。主动关闭方通常进入 TIME_WAIT,便于重传最终 ACK,并等待旧报文失效。

**易错提醒：** 挥手次数由双向关闭和确认决定;不要只用验证收发能力解释全部握手设计。

### 86 Cookie Session Token 与 JWT

Cookie 是浏览器存储和发送数据的机制;Session 是服务端保存会话状态的方案;Token 是访问凭证。它们并非互斥,同一系统可以把会话 ID 或 Token 放入 Cookie。

- Session 常由随机会话 ID 关联服务端状态。多实例部署要设计共享会话或路由策略;Cookie 是否跨站发送受 Domain、Path、SameSite、Secure 等规则约束。

- 常见签名 JWT 由 Header、Payload、Signature 三部分组成。前两部分是 Base64URL 编码,可直接解码,不应放密码和敏感秘密。签名可使用 HMAC 或非对称算法,并不总是私钥加密。

- 服务端要验证签名、允许的算法、有效期,以及适用的 issuer 和 audience。签名 JWT 不自带即时撤销能力,可用短有效期及服务端状态设计退出和封禁。

- HttpOnly 可降低脚本直接读取 Cookie 的风险;Cookie 自动携带的认证需考虑 CSRF,浏览器可读存储中的 Token 则需考虑被 XSS 窃取。

**易错提醒：** JWT 默认签名不等于加密,Base64URL 不是加密,Token 也不一定采用 JWT。

### 87 新增 TCP 如何保证可靠传输 流量控制与拥塞控制有何区别

TCP 在连接内提供有序字节流,通过序列号、确认、重传和校验等机制应对丢包、重复与乱序。流量控制避免发送方压垮接收端,拥塞控制避免网络路径持续过载,两者共同限制发送速率。

- 接收窗又 rwnd 反映接收端可接收能力;拥塞窗又 cwnd 由发送端根据网络反馈调整,在途数据受两者共同约束。传统拥塞控制包括慢启动、拥塞避免、快速重传等,具体算法依系统实现。

- TCP 没有业务消息边界,一次 write 不对应一次 read;应用协议需用长度字段、分隔符等方式分帧。TCP ACK 只确认传输层接收,不代表订单等业务已经处理成功。

**易错提醒：** 重传不是重新执行业务的许可;连接中断后重试请求,仍需防止服务端已执行而客户端未收到结果。

### 88 新增 输入网址到得到响应经历什么 怎样定位慢请求

以首次访问 HTTPS 服务为例:解析 URL 与缓存策略,通过 DNS 获取目标地址,建立传输连接与TLS 会话,发送 HTTP 请求,经过代理或网关到服务端处理,再接收响应。浏览器随后按资源与页面内容继续加载和渲染。

- DNS 可能命中浏览器、系统或递归解析器缓存;未命中时解析器按域名层级查询。已有连接可复用,HTTP 3 使用 QUIC,实际流程不会每次重复完整 TCP 与 TLS 建连。

- 排查时拆分 DNS、连接、TLS、首字节和下载时间,并结合服务端排队、应用处理、数据库与下游调用耗时。首字节慢可能包含网络与服务端多段等待,不能只看总时长下结论。

**易错提醒：** 浏览器收到响应不等于页面已经渲染完成;接又总耗时也不等于业务代码的执行耗时。

### 89 新增 BIO NIO AIO 与多路复用怎样区分

阻塞 I/O 通常让调用线程等待数据或操作完成;非阻塞 I/O 在暂不可进行时及时返回;多路复用让一个线程等待多个连接的就绪事件,再按就绪情况处理。异步 I/O 则由系统或实现负责发起的操作,并在完成后通知调用者。

- Java NIO 常用 Channel、Buffer、Selector。Selector 报告就绪不等于已替应用完成所有读写,仍需处理部分读取、部分写入和协议分帧;NIO 中的通道也并非全部只能非阻塞。

- Linux 常用 epoll 管理关注集合及就绪事件,避免应用反复检查全部空闲连接;Reactor 线程负责事件分发时,耗时业务应合理交给工作线程,防止阻塞其他连接。

**易错提醒：** NIO 不是异步 I/O 的同义词,epoll 也不能保证所有负载下都更快;事件线程同样可能被业务阻塞。

## 10 业务设计与稳定性

### 90 未支付订单怎样自动取消

常用方案是持久化订单到期时间,以延迟任务触发取消,并用定时扫描补偿遗漏。任务到达时重新检查订单状态和到期时间,通过数据库条件更新解决重复触发及支付竞争。

- DelayQueue 适合简单单进程任务,但仅在内存中,重启后需恢复任务,多实例还需协调;take 可阻塞等待到期,不必忙轮询。

- 延迟消息或 Redis 有序集合便于集中调度,但要设计持久性、可靠投递或原子领取、失败重试和重复消费。延迟范围与精度依具体产品配置,不存在通用 24 小时上限。

- 定时扫描依赖到期时间及状态索引,分批处理;精度受扫描周期影响,吞吐与资源占用需要压测。

- 取消应使用类似 status=UNPAID 且 expire_at<=当前时间的条件更新,并根据受影响行数决定后续动作。支付成功与取消共享状态机,晚到支付应明确拒绝或退款规则;跨系统资源释放需可重试和幂等。

**易错提醒：** 收到到期消息不等于订单一定能取消;先读状态再无条件改写存在支付竞争窗又。

### 91 怎样建设系统稳定性

先确定关键链路和可用性、延迟等目标,再围绕可观测性、容量、依赖故障、变更和恢复设计措施。每项措施都应能通过演练和监控验证。

- 发现问题:监控错误率、延迟、饱和度及业务成功率,配合日志和链路追踪,设置可行动的告警与责任人。

- 承载流量:容量评估与压测、限流和背压、弹性扩容、热点治理、数据库索引与归档。分库分表应由实际容量及运维需求驱动。

- 控制故障传播:明确超时预算、有限重试与退避、熔断和降级、线程及连接资源隔离;重试必须考虑幂等和放大流量。

- 减少变更风险并恢复服务:自动化检查、灰度及回滚、多实例或多故障域部署、备份恢复演练。根据 RTO 和 RPO 选择灾备能力。

**易错提醒：** 多副本不能替代备份,部署多机也不自动保证跨机房容灾;稳定性不能只罗列中间件。

### 92 新增 接口幂等怎样抵御重复请求与并发

接又幂等指同一业务操作被重复请求时,业务效果与成功执行一次一致,响应内容不必逐字相同。通常以调用方、操作类型和业务请求号确定唯一操作,并把去重记录与业务变更放在同一本地事务里,让并发请求也只能生效一次。

- 用数据库唯一键仲裁创建操作,记录处理状态和结果;同一幂等键携带不同参数应拒绝,重复请求返回原结果或处理中状态,并约定去重记录保留期。

- 状态流转用带旧状态或版本条件的 UPDATE,按实际变更结果推进;MQ 重投可沿用稳定的业务操作标识,外部接又副作用还需下游支持幂等。

**易错提醒：** 先查询是否存在再执行,或仅在执行前写入 Redis 标记,都不能独自保证业务效果只生效一次。

### 93 新增 本地事务与 MQ 发消息如何保持一致

本地事务与发送 MQ 属于两个资源,先提交哪一个都存在中间失败窗又。Outbox 将业务变更和待发送事件写入同一数据库事务,提交后由独立发布器扫描或通过 CDC 投递消息,使已提交业务最终能发出事件;前提是发布任务可恢复并持续重试。

- 发布器确认 MQ 已接收后再标记已发;若发布成功后、标记前宕机,恢复后会再次投递,因此事件ID 必须稳定,消费者仍需业务幂等。

- 只发布已提交的事件,失败时保留待发送记录并监控重试、积压和告警;同一业务实体要求顺序时,还需序号及发布、消费顺序控制。

**易错提醒：** Outbox 提供可靠最终投递,不能承诺消息永不重复,也不能让外部系统立即完成同一原子事务。

### 94 新增 限流 熔断 降级有什么区别 重试为何放大故障

限流按速率或并发量限制进入系统的工作,熔断根据下游故障情况暂时阻止调用并探测恢复,降级则减少功能或返回可接受的替代结果,优先保住核心业务。三者可组合使用;重试会增加请求和资源占用,必须限制次数、总时限和重试层级。

- 令牌桶按设定速率补充令牌,容量允许有限突发;漏桶以相对固定速率出队,队列满时拒绝,适合平滑流量;单机额度不等于集群总额度。

- 多层同时重试会乘法放大下游请求;只重试适合重试的故障,确认操作幂等,配合指数退避和随机抖动,尊重限流及熔断信号。

**易错提醒：** 超时不等于下游未执行,降级也不能伪造支付成功等关键业务结果。
