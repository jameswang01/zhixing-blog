## Redis 编码 内存与高可用

<span id="41-五种常见数据类型的底层编码是什么"></span>

<span id="1-五种常见数据类型的底层编码是什么"></span>

### 1 常见数据类型的底层编码是什么

<span class="java-label java-insight">理解与追问：</span> 面试时先说外部数据类型，再说明内部编码会随数据规模和版本变化。例如同样是 Hash，紧凑编码与哈希表的空间和操作特性不同，不应将某种底层结构视为永久固定。

逻辑类型与物理编码要分开:String 常见 int、embstr、raw;Hash 小对象常用 listpack,扩大后用哈希表;ZSet 小对象常用 listpack,通用编码由跳表与字典配合;List 使用 quicklist 等编码,而非跳表;Set 可用 intset、哈希表,部分版本也用 listpack。

- Redis 7 起 Hash、ZSet 的紧凑编码重点记 listpack,而非旧教材的 ziplist。List 的 quicklist 连接多个紧凑数据块;较新版本的小 List 也可能直接使用 listpack,应看实际版本。

- 纯整数小 Set 可使用 intset,Redis 7.2 起小 Set 还支持 listpack。切换条件受元素数量、长度和配置影响,不能给所有类型套同一组阈值;可用 OBJECT ENCODING key 查看实例编码。

<span class="java-label java-warning">易错提醒：</span> 这五类只是面试中常见的基础类型，并不是 Redis 的完整类型清单；例如 Stream 也用于追加消息和消费组。编码阈值与内部实现需按实际版本核实。

<span class="java-label java-example">具体场景：</span> Redis 的 Hash 对外都是字段—值映射，但小集合和大集合可能采用不同内部编码。排查内存占用时要结合版本、元素数量及配置，而不是只看业务上的数据类型名称。

**追问：Hash 一定由哈希表实现吗？** 不能只凭对外数据类型断言内部编码。编码会随元素大小、数量、配置和 Redis 版本变化，应结合实际实例与官方文档查看。

<span id="42-压缩列表-listpack-字典和跳表分别解决什么问题"></span>

### 2 压缩列表 listpack 字典和跳表分别解决什么问题

<span class="java-label java-insight">理解与追问：</span> 紧凑结构更节省小集合空间，字典适合按键查找，跳表适合有序范围操作。选型需要同时看元素数、单元素大小、访问模式以及对应 Redis 版本的编码转换条件。

ziplist 和 listpack 都用紧凑连续内存减少小对象的指针开销;字典通过哈希定位提供平均常数级查找;跳表通过多层有序链支持平均 O(log N) 定位和按序遍历。ZSet 用字典查成员分数、跳表维护有序访问,各自承担不同职责。

- 旧 ziplist 的前项长度编码可能导致连锁更新。listpack 改进了元素布局,避免这种前项长度变化的连锁传播;连续内存的插入删除仍可能搬移数据,不等于所有操作都 O(1)。

- 字典需要处理哈希冲突与扩容,Redis 采用渐进式 rehash 思路分摊迁移工作;跳表底层串起全部成员,高层作快速导航。复习优先理解复杂度和用途,不必背容易随版本变化的 C 结构体字段。

<span class="java-label java-warning">易错提醒：</span> 跳表不属于 List 的通用实现;紧凑编码省内存也会带来查找和移动成本。

<span class="java-label java-example">具体场景：</span> 少量短字段适合紧凑表示以节省节点开销；元素增加后可能转换成更适合查找的结构。有序集合除了按成员定位，还可能需要按分数做范围查询，因此不同结构承担不同职责。

**追问：紧凑编码为什么可能更省内存？** 小集合可以减少独立节点和指针开销，但查找、修改成本受结构与数据规模影响。何时转换依赖版本与配置，不能机械套用固定阈值。

<span id="43-redis-如何删除过期键"></span>

### 3 Redis 如何删除过期键

<span class="java-label java-insight">理解与追问：</span> 如果一个过期键暂时没有被访问，惰性删除不会立刻触发；后台周期性过期处理再帮助清理。过期时间到了不保证该键占用的内存会在同一时刻立即归还。

Redis 结合被动过期与主动过期:访问键时若已到期,就按不存在处理并触发清理;后台还会周期性抽样检查带过期时间的键,主动删除已过期项,避免长期无人访问的过期键一直占用内存。

- 主动扫描受事件循环、工作预算及相关配置影响,不是为每个键创建定时器,也不能承诺固定每 10秒扫一次或固定抽样数量与比例。逻辑到期与物理内存回收时间并不完全相同。

- 过期时间基于时间戳,实例停机不会暂停 TTL。主从复制中,主节点通常集中决定过期删除并传播删除操作;到期通知可能晚于设定时刻,不应把它当成精确可靠的订单到期调度器。

<span class="java-label java-warning">易错提醒：</span> 键过期清理与内存不足时淘汰是两套机制,触发条件和可删除对象不同。

<span class="java-label java-example">具体场景：</span> 某 key 设置了过期时间，时间到了但暂未被访问，它不保证在那一刻立刻从内存删除。访问时可能惰性清理，后台也会周期性处理过期键；具体时机受到运行状态影响。

**追问：到期后内存会立刻释放吗？** 不保证。访问时可能触发惰性删除，后台也会周期性处理过期键；大量到期键和资源压力会影响清理时机。

<span id="4-常见八种内存淘汰策略如何分类"></span>

### 4 Redis 内存淘汰策略如何分类

<span class="java-label java-insight">理解与追问：</span> 先看是否允许淘汰，再区分候选范围是全部键还是设置了过期时间的键，最后比较 LRU、LFU、随机等策略。缓存容量规划仍需结合命中率和写入失败监控。

Redis 7 的常见八种策略可按候选集合记忆:全部键中选 allkeys-lru、allkeys-lfu、allkeys-random;仅带 TTL 的键中选 volatile-lru、volatile-lfu、volatile-random、volatile-ttl;另有 noeviction。达到 maxmemory 压力时按所选策略处理。

- LRU 偏向淘汰很久未访问的键,LFU 偏向低访问频率,random 随机,volatile-ttl 偏向剩余寿命短的键。Redis 的 LRU/LFU 使用近似机制,不能当成精确维护全部键的全局排序。

- noeviction 不主动淘汰,可能增加内存的命令会报错,普通读取仍可工作;volatile 系列在没有合格候选键时也可能无法腾出空间。maxmemory 应为复制、持久化缓冲与运行开销预留余量。

- 这里的八种按 Redis 7 范围整理；[Redis 官方文档](https://redis.io/docs/latest/develop/reference/eviction/)还记载，Redis 8.6 增加 `allkeys-lrm` 和 `volatile-lrm`，按最近修改时间近似淘汰。使用时以实际部署版本及配置为准。缓存与重要状态混放时，还要评估重要键被淘汰的风险。

<span class="java-label java-warning">易错提醒：</span> volatile-ttl 会淘汰尚未到期的键,不能把它称为过期删除策略。

<span class="java-label java-example">具体场景：</span> 缓存达到 maxmemory，若策略只考虑设置过期时间的键，而现有键都没设置过期时间，就可能没有合适候选。写入是否失败应结合淘汰策略、错误和内存指标判断。

**追问：有 maxmemory 就一定能淘汰出空间吗？** 还要看淘汰策略与候选键。例如只从设置过期时间的键里挑选时，若没有合适候选，写请求仍可能失败。策略应结合业务和监控确定。

<span id="45-主从与-sentinel-有什么区别"></span>

### 5 主从与 Sentinel 有什么区别

<span class="java-label java-insight">理解与追问：</span> 复制解决数据副本传播，Sentinel 负责监控并协调故障转移；它们并不自动提供分片。异步复制下故障切换可能丢失尚未复制的数据，应根据业务容忍度设计。

基础主从提供数据复制、备份与读扩展,通常写主读从,但它本身不负责完整的自动故障转移。Sentinel 在主从之上增加监控、故障判断、主节点选举切换及服务发现,客户端需要感知新的主节点地址。Sentinel 不负责把一个数据集水平分片。

- 单个 Sentinel 可先判断主观下线,达到配置的 quorum 后形成客观下线判断;真正执行故障转移还需要获得 Sentinel 多数授权,因此 quorum 与选举多数不是一回事。

- 异步复制下,旧主已确认但未复制的写入在切换时可能丢失,读副本也可能读旧值。吞吐上限取决于命令、数据、硬件与网络,不能把某个固定“十万并发”作为架构保证。

<span class="java-label java-warning">易错提醒：</span> Sentinel 改善可用性,不自动提供强一致性,也不能突破单主数据集的容量上限。

<span class="java-label java-example">具体场景：</span> 主节点写入后尚未来得及把变更复制到副本就宕机，即使 Sentinel 完成切换，也可能缺少那次写入。复制负责传递数据，Sentinel 负责监控和协调切换，两者不等于强一致提交。

**追问：Sentinel 能保证切换时零数据丢失吗？** 不应这样承诺。它负责监控与协调切换，而复制链路可能异步；旧主尚未复制的写入在故障时存在丢失窗口。

<span id="46-redis-cluster-如何分片-有哪些限制"></span>

### 6 Redis Cluster 如何分片 有哪些限制

<span class="java-label java-insight">理解与追问：</span> Cluster 将键映射到哈希槽，并把槽分配给节点；扩容涉及槽迁移。多键操作是否允许还取决于键是否位于同一槽，使用 hash tag 要同时考虑热点集中风险。

Redis Cluster 把键空间划为 16384 个哈希槽,一般按 CRC16(key) mod 16384 定位槽,再由槽映射到主节点。扩缩容通过迁移槽及其数据完成;每个主节点可配副本,并由 Cluster 协议处理故障转移。

- 它不是一致性哈希环,也不是 232−1 个虚拟槽。hash tag 可让多个键按同一段 {...} 内容计算槽,便于要求同槽的多键操作,但标签使用不当也可能造成倾斜。

- Cluster 的多键事务和多键脚本通常要求相关键在同槽。节点故障的影响取决于副本、网络分区、槽覆盖和配置,不能承诺“只影响故障节点那部分”;热点键也不会因增加槽自动拆分。

<span class="java-label java-warning">易错提醒：</span> Cluster 分片与副本是两个维度,增加副本不会把同一热点键的写压力均匀分散。

<span class="java-label java-example">具体场景：</span> 例如一次操作涉及两个订单 key，它们落在不同哈希槽时，相关多键命令可能无法执行。使用 hash tag 可以让关联 key 共槽，但也要防止大量请求集中到同一个槽。

**追问：为什么多键操作可能失败？** Cluster 将键映射到不同槽，某些多键操作要求键位于同一槽。hash tag 可让相关键共槽，但集中到同一槽也可能造成热点。

<span id="47-redis-全量复制与部分重同步如何工作"></span>

### 7 Redis 全量复制与部分重同步如何工作

<span class="java-label java-insight">理解与追问：</span> 部分重同步依赖复制偏移与积压缓冲等条件，缺少可用历史时会退回全量同步。全量同步可能占用网络和磁盘资源，扩容或故障恢复时应预留容量。

副本使用 PSYNC 携带复制 ID 与偏移量请求同步;若主节点仍认识该复制历史,且复制积压缓冲保留了所缺区间,就可部分重同步,否则需要全量同步。首次同步一般走全量,但网络断开后不一定每次都重新传整个数据集。

- 全量同步通常由主节点生成并传输 RDB 快照,副本加载后继续处理快照生成期间及之后的增量写入;也支持无盘传输方式。复制 ID 标识数据历史,不能简单等同于进程 runid。

- 复制积压缓冲用于补齐断链期间缺失的数据,大小可配置,应按写流量和预期断链时间估算;不要把它与副本输出缓冲或全量同步期间的增量缓冲完全混同,也不要写死为 1 MB。

- Redis 默认异步复制。WAIT 可等待一定数量副本确认,降低丢写概率,但不把整个部署变为强一致系统,也不保证所有故障场景下已确认写永不丢失。

<span class="java-label java-warning">易错提醒：</span> 部分重同步依赖复制历史匹配与缓冲覆盖,只有偏移量接近还不够。

<span class="java-label java-example">具体场景：</span> 副本短暂断线后，如果主节点仍保有对应复制历史，可能进行部分重同步；如果历史已经被覆盖或不匹配，就需要全量同步。全量过程可能增加网络和磁盘压力。

**追问：断线后总能部分重同步吗？** 不能。需要复制历史和位点仍然可用；如果缓冲中的历史不足或条件不满足，可能需要全量同步，增加资源压力。

<span id="48-新增-rdb-aof-如何取舍-恢复时有哪些持久性边界"></span>

### 8 RDB AOF 如何取舍 恢复时有哪些持久性边界

<span class="java-label java-insight">理解与追问：</span> RDB 更像时间点快照，AOF 记录写操作以供恢复；不同刷盘策略对应不同性能和潜在丢失窗口。真正的恢复能力还取决于备份保留、恢复演练和部署故障域。

RDB 保存某一时刻的数据快照,文件紧凑、适合备份,但崩溃可能丢失上次快照后的写入;AOF记录写操作,持久性取决于刷盘策略,也需要重写控制体积。选型要同时考虑可容忍丢失窗口、恢复时间、磁盘开销和业务是否能从数据库重建。

- 未跳过刷盘且存储可靠时,AOF always 在回复前完成同步刷盘;everysec 通常有约一秒未落盘窗口,实际风险受调度、磁盘及配置影响;no 交由操作系统刷盘。重写期间若配置跳过 fsync,刷盘保证会减弱;复制不能替代本机持久化和独立备份。

- BGSAVE、AOF 后台重写可减少主线程长时间写盘,但 fork 与写时复制仍消耗时间和额外内存。Redis 7 起 AOF 可由基础文件、增量文件及清单组成;同时启用两种持久化时通常优先用 AOF 恢复,应定期验证备份完整性和实际恢复过程。

<span class="java-label java-warning">易错提醒：</span> AOF 重写不是把业务历史日志永久保存;不能只备份一个看似最新的文件就认定可完整恢复。

<span class="java-label java-example">具体场景：</span> 若 AOF 策略不是每次写都同步持久化，断电可能丢失尚未刷盘的数据。应按业务允许的丢失窗口选择配置，同时验证备份完整性和实际恢复流程。

**追问：开启 AOF 就不会丢数据吗？** 仍取决于刷盘策略、故障时机与底层存储。备份和恢复演练也不可缺少，持久化文件不等于已经验证可恢复。

<span id="49-新增-缓存穿透-击穿-雪崩分别怎么治理"></span>

### 9 缓存穿透 击穿 雪崩分别怎么治理

<span class="java-label java-insight">理解与追问：</span> 穿透是请求不存在的数据持续穿过缓存；击穿是热点键失效后并发回源；雪崩是大量缓存同时失效或缓存整体不可用。它们的成因不同，空值缓存、请求合并和分散过期时间分别解决不同问题。

穿透是查询不存在的数据,缓存与数据库均不命中;击穿是某个热点键失效后,大量并发请求一起回源;雪崩是大量键集中失效或缓存服务故障,导致回源流量激增。先识别触发原因,再分别减少无效回源、合并重建请求及限制数据库入口流量。

- 穿透可结合参数校验、短 TTL 空值缓存与布隆过滤器;空值要防止新数据创建后仍被遮蔽。布隆过滤器可能把不存在误判为存在,必须正确维护新增数据,不能因过滤器漏同步就把合法数据永久挡掉;具体能力也取决于部署版本与组件。

- 击穿可用互斥或单飞机制只让少量请求重建,等待者限时等待或按业务允许返回旧值;锁要有到期与持有者校验。雪崩可错开 TTL、提前预热并设置回源并发上限、熔断与降级;整套 Redis 不可用时,TTL 随机化无法提供保护。

<span class="java-label java-warning">易错提醒：</span> 逻辑过期返回旧值只适用于容忍陈旧数据的业务,缓存故障时全量放行数据库可能扩大故障。

<span class="java-label java-example">具体场景：</span> 对不存在的商品 ID 持续请求是穿透；一个热门商品缓存过期后大量请求同时回源是击穿；大量 key 同时失效或缓存整体故障可能导致雪崩。三者需分别观察和治理。

**追问：三个缓存问题怎么快速区分？** 不存在的键反复查是穿透；单个热点过期带来集中回源是击穿；大量缓存同时失效或整体故障是雪崩。先识别流量形态再选治理手段。

<span id="50-新增-缓存与数据库一致性如何设计"></span>

### 10 缓存与数据库一致性如何设计

**把一次旧值回填走完：** ① 缓存没有商品价格，读请求 A 去数据库读到旧价格 10；② 写请求 B 将数据库改为 12 并提交，随后删除缓存；③ A 比 B 更晚结束，把刚才读到的 10 回填进缓存。此时数据库是 12，缓存却是 10。

“先更新数据库，再删缓存”可以处理常见顺序问题，但它本身并不能阻止上面的并发回填。可以根据业务选择短 TTL 缩短旧值持续时间、用版本号约束回填、可靠重试删除，或让关键写后读回数据库；每种方案需要分别验证并发与失败路径，不能把任意一种口头方案视为强一致保证。

<span class="java-label java-insight">理解与追问：</span> 例如先更新数据库、再删除缓存可以降低常见的不一致窗口，但并发旧值回填仍可能发生。是否需要延迟重试、版本控制或可靠消息，应根据业务对旧数据的容忍度和可观测性决定。

常见旁路缓存是读时先查缓存,未命中再读数据库并回填;写时先提交数据库,再删除缓存。这样便于以数据库为事实来源,但两次操作不原子,删除失败、并发回填及副本延迟仍会产生旧值,需要按业务可容忍的陈旧窗口设计补偿和关键读路径。

- 写库成功后进程崩溃可能漏删缓存,可用事务 outbox 或可靠的变更订阅推动失效,并对消费重试、重复、乱序做处理;TTL 作为兜底。若变更事件只存于进程内存,或异步消息没有可靠产生与重试机制,就不能保证最终一定完成失效。

- 即使删缓存成功,先读到旧数据的并发请求仍可能稍后回填;可结合版本校验、受控重建等缩小窗口,回源读副本还要处理复制延迟。跨数据库与缓存的全路径协调成本较高,扣库存、判断唯一性等关键决策应由数据库约束或事务完成,必要时直接读主库。

<span class="java-label java-warning">易错提醒：</span> 先写库再删缓存、延时双删、加锁或 CDC 单独使用,都不能自动保证跨存储强一致。

<span class="java-label java-example">具体场景：</span> 线程 A 从数据库读到旧值，线程 B 更新数据库并删除缓存，随后 A 又把旧值写入缓存，仍可能出现旧数据。根据业务要求考虑版本判断、可靠删除重试和不一致监控。

**追问：先更新数据库再删缓存就强一致了吗？** 不一定。并发读取可能在删除后把旧值写回；删除失败也会扩大不一致窗口。要根据场景评估版本控制、可靠重试和业务容忍度。

<span id="51-新增-pipeline-multi-exec-watch-与-lua-有什么区别"></span>

### 11 Pipeline MULTI EXEC WATCH 与 Lua 有什么区别

<span class="java-label java-insight">理解与追问：</span> Pipeline 主要减少往返次数，不保证一组命令具备事务语义；MULTI/EXEC 将命令批量执行，WATCH 可做乐观检查；Lua 在服务端执行应控制运行时间。原子执行不等于能跨 Redis 与数据库回滚。

Pipeline 批量发送命令以减少网络往返,不保证这批命令连续执行;MULTI/EXEC 将排队命令作为一组执行,期间其他客户端命令不会插入;WATCH 在执行前检查关注键是否变化;Lua 把读取、判断、修改放到服务端,适合依赖前一步结果的条件逻辑。

- 事务入队阶段的错误可能使整批不能执行;EXEC 后的运行时错误通常不会撤销已成功命令,也不阻止其余命令继续执行。WATCH 检测到变化会放弃该次执行,应用需重新读并决定是否重试;DISCARD 只是丢弃尚未执行的队列,不是回滚已经发生的修改。

- Lua 执行期间不与其他命令交错,但运行时报错也不会自动撤销此前写入,应先校验参数、类型和业务条件。脚本要短;Pipeline 应分合理批次,避免回复积压。连接超时可能让执行结果不确定,非幂等操作不能盲目整批重放,Cluster 多键操作还需满足同槽要求。

<span class="java-label java-warning">易错提醒：</span> Redis 中的执行隔离不等于数据库式失败回滚,也不等于已经可靠刷盘。

<span class="java-label java-example">具体场景：</span> 一次 Pipeline 把 100 次 GET 集中发送能减少网络往返，但其中命令不自动构成回滚事务；如果需要校验条件后执行 Redis 内一组操作，可评估 WATCH 或短小的 Lua 脚本。

**追问：Pipeline 是否等于事务？** 不是。Pipeline 主要合并网络往返，不自动把多条命令变成原子单元；MULTI/EXEC、WATCH 和 Lua 各自提供不同能力，也都不能自动跨数据库回滚。

<span id="52-新增-如何识别和治理热-key-大-key"></span>

### 12 如何识别和治理热 key 大 key

<span class="java-label java-insight">理解与追问：</span> 热 key 先通过访问频率和实例负载定位，再考虑本地缓存、请求合并或合理拆分；大 key 则需关注网络传输、单次操作耗时和删除方式。治理前先确认一致性与业务语义。

热 key 是访问或资源消耗集中在少数键,大 key 是单键内容或成员过多,两者可以同时存在。先用请求采样、慢日志、内存与网络指标确定具体键和访问模式,再决定降低访问频率、拆分数据还是减少单次返回量,不能只靠增加节点期待自动均摊。

- redis-cli --hotkeys 依赖 LFU 统计,应确认当前策略适用,不要仅为排查随意切换淘汰策略。--bigkeys 偏向按类型找大字符串或成员多的集合,结合 --memkeys、MEMORY USAGE 和业务采样更接近实际内存;扫描要限速,避免直接使用全量 KEYS 或长时间 MONITOR。

- 读热点可用短 TTL 本地缓存、请求合并或预热;写热点只有在业务允许时才能分桶并另行聚合。大集合可按业务边界分片,分页或增量遍历并限制一次取数;删除时评估 UNLINK 等异步释放方式。拆分后仍要维护聚合语义、一致性和失效机制,不能只减少键的大小。

<span class="java-label java-warning">易错提醒：</span> 不存在适合所有业务的统一大 key 阈值;UNLINK 也不能消除复制、网络及所有主线程开销。

<span class="java-label java-example">具体场景：</span> 一个 key 被大量请求命中形成热点，瓶颈可能集中在单节点；一个包含数百万成员的集合则是大 key。前者关注请求分散或合并，后者关注拆分、扫描和删除成本。

**追问：删除大 key 为什么也要小心？** 一次性处理大量元素可能占用服务端时间或引发资源波动。应先评估对象类型、版本和删除方式，并结合拆分、异步释放或分批治理。

<span id="53-新增-redis-为什么快-单线程边界和阻塞风险是什么"></span>

### 13 Redis 为什么快 单线程边界和阻塞风险是什么

<span class="java-label java-insight">理解与追问：</span> Redis 的快与内存访问、数据结构及事件驱动等多种因素有关。单线程命令执行路径仍可能被大查询或复杂脚本阻塞，网络和持久化相关工作是否多线程取决于版本及配置。

Redis 的常见操作主要在内存完成,专用数据结构降低查找与修改成本,事件循环和 I/O 多路复用高效管理连接,命令执行主路径减少线程竞争。这里的单线程主要指常规命令访问数据的执行模型,并不表示持久化、网络处理和内存释放全部只用一个线程。

- Redis 6 起可用 I/O 线程分担网络读写,后台线程或子进程参与刷盘、异步释放、快照与重写;具体行为依版本和配置。命令执行仍可能受单核、网络或内存带宽限制,多实例、Cluster 可以分散多个键的负载,但不会自动拆分单个热点写键。

- KEYS、大范围集合运算、巨大返回、长 Lua 脚本以及同步释放大对象等可能占用执行主线程,拖慢其他客户端;应控制复杂度与批量大小,用 SCAN 等增量方案。BLPOP 等阻塞式等待通常挂起的是当前客户端,不会在等待元素期间卡住整个服务,要与慢命令区分。

<span class="java-label java-warning">易错提醒：</span> 内存数据库也会受缺页、swap、fork 和磁盘刷盘影响;低平均延迟不能证明没有尾延迟风险。

<span class="java-label java-example">具体场景：</span> 一个脚本遍历巨大集合时，即使数据在内存中，也可能占住命令执行路径，让其他请求等待。排查应看慢命令、脚本耗时和大 key，而不是只问“Redis 是否单线程”。

**追问：Redis 快是不是因为完全单线程？** 不能归结为单一因素。内存访问、数据结构与事件驱动都影响性能；耗时命令和长脚本仍可能阻塞命令处理，其他工作是否多线程依版本配置。
