## Spring 与 MyBatis

<span id="54-spring-mvc-的请求处理流程"></span>

### 1 Spring MVC 的请求处理流程

**理解与追问：** 一次请求通常经 DispatcherServlet 查找处理器，再经参数解析、业务处理和返回值处理生成响应。拦截器、异常处理和消息转换分别处在不同环节，排查时要结合具体配置。

请求先进入 DispatcherServlet,由 HandlerMapping 找到处理器及拦截器链,再由 HandlerAdapter调用 Controller。返回结果如何输出,取决于控制器方法的返回类型和注解。

- 视图场景:返回 ModelAndView 或视图名,经 ViewResolver 找到 View,再渲染响应。

- 接口场景:@ResponseBody 或 @RestController 的返回值通常由 HttpMessageConverter 序列化为 JSON 等响应体。

- 异常可交给 HandlerExceptionResolver 体系处理,例如 @ExceptionHandler。

**易错提醒：** 不是所有请求都经过视图解析和页面渲染;REST 接口一般直接写响应体。

**具体场景：** 请求到达 DispatcherServlet 后，需要先找到匹配的处理器，再解析参数、调用控制器，最后处理返回值。控制器正常返回后如果 JSON 序列化失败，问题可能位于消息转换阶段。

**追问：Controller 返回对象后怎么变成 JSON？** 常见流程通过返回值处理器和消息转换器序列化，具体还取决于注解、内容协商和配置。序列化失败不一定发生在业务方法执行期间。

<span id="55-七种事务传播行为与实现原理"></span>

### 2 七种事务传播行为与实现原理

**理解与追问：** 例如外层事务调用 REQUIRED 方法通常参与同一事务；REQUIRES_NEW 会使用独立事务语义，涉及资源挂起与恢复。独立提交后外层回滚不自动撤销内层已提交结果。

事务传播行为描述：调用进入一个事务方法时，如何处理当前是否已有事务。下表中的事务行为需要调用经过 Spring 事务拦截器，具体挂起和保存点能力还取决于事务管理器。

| 传播行为 | 已有事务 | 没有事务 |
| --- | --- | --- |
| REQUIRED（默认） | 加入当前事务 | 创建事务 |
| REQUIRES_NEW | 挂起当前事务，创建独立事务 | 创建事务 |
| NESTED | 支持时，在同一物理事务内创建保存点 | 通常按 REQUIRED 创建事务 |
| SUPPORTS | 加入当前事务 | 非事务执行 |
| NOT_SUPPORTED | 挂起当前事务，非事务执行 | 非事务执行 |
| MANDATORY | 加入当前事务 | 抛出异常 |
| NEVER | 抛出异常 | 非事务执行 |

例如外层下单事务调用另一个 Bean 的 REQUIRED 方法，内外层通常共享同一个物理事务；内层将它标记为 rollback-only 后，外层即使捕获异常，最终提交仍可能抛 `UnexpectedRollbackException`。若内层使用 REQUIRES_NEW，它可以独立提交；外层同时持有数据库连接时，还要评估内层另取连接导致的连接池压力。参考 [Spring 事务传播官方文档](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html)。

- 常规命令式事务由代理拦截器调用事务管理器;连接等资源通常绑定到当前线程。普通新线程不会自动继承该事务。

- REQUIRED 的内部逻辑事务若标记 rollback-only,外层即使捕获异常,最终仍可能无法提交并抛UnexpectedRollbackException。

- REQUIRES_NEW 独立提交或回滚,外层资源暂挂;需留意连接池额外占用及锁等待。NESTED 常依赖 JDBC 保存点和事务管理器支持,外层回滚仍会撤销内层修改。

**易错提醒：** REQUIRED 不是独立子事务;NESTED 不是 REQUIRES_NEW;挂起能力和保存点能力取决于事务管理器。

**具体场景：** 外层下单事务调用内层独立审计事务：如果内层 REQUIRES_NEW 已提交，外层后来回滚，内层通常不会随之回滚。前提是调用确实经过事务代理且事务管理器支持相应行为。

**追问：内层 REQUIRES_NEW 提交后外层回滚，内层会回滚吗？** 通常不会，因为它是独立事务语义；但实际行为仍取决于调用是否经过代理及事务管理器支持。

<span id="56-事务未生效或没有回滚时怎样排查"></span>

### 3 事务未生效或没有回滚时怎样排查

**理解与追问：** 先确认调用是否经过代理、目标方法与事务管理器是否匹配，再检查异常是否被吞掉、回滚规则及是否跨线程。自调用失效指默认代理模式下绕过代理，并非所有增强模式都一样。

按代理入口、事务基础设施、异常规则、资源与线程边界依次排查。先确认调用确实经过 Spring 管理的代理,再检查实际事务是否开启以及回滚条件是否满足。

- 常见原因:手动 new 对象、未启用事务支持、类内 this 调用绕过代理、选错事务管理器,或者数据源和操作资源不匹配。

- 默认规则是 RuntimeException 和 Error 回滚,受检异常默认不回滚;可按业务设置 rollbackFor。异常被吞掉且未标记回滚时,代理通常看不到失败。

- JDK 接口代理要求事务方法是接口公开方法;Spring 6 起,类代理默认也支持受保护及包可见方法。private 方法和类代理中的 final 方法不能被相应代理增强。

- 异步线程、非事务存储引擎,以及非事务传播配置,都可能使实际行为不符合预期。

**易错提醒：** public 不是事务失效原因;也不能把非 public 一概判为所有 Spring 版本都无效。

**具体场景：** 同一个 Service 的普通方法直接调用自身标注事务的方法，默认代理模式下可能绕过事务拦截。先确认是否经过代理，再检查事务管理器、异常处理和线程切换，不能只看有没有注解。

**追问：同类方法调用为什么常导致事务注解不生效？** 默认代理模式下，自调用没有经过代理拦截。还需检查异常是否被捕获、回滚规则、事务管理器和异步线程边界。

<span id="57-jdk-动态代理与-cglib-的区别"></span>

### 4 JDK 动态代理与 CGLIB 的区别

**理解与追问：** 面试可从代理对象如何创建和调用如何拦截切入：接口代理与基于子类的代理各有适用边界。最终采用哪种方式由框架版本和配置决定，final 等限制也要结合具体机制。

JDK 动态代理生成实现接口的代理对象,调用通过 InvocationHandler 分发;CGLIB 生成目标类的子类,以方法拦截实现增强。选型主要看接口、可继承性及框架配置。

- JDK 代理可通过接口代理 final 类的接口方法;CGLIB 不能继承 final 类,也不能覆盖 final 或private 方法。

- Spring AOP 的两种代理都有自调用绕过增强的问题。优先把需要代理调用的方法拆到协作 Bean;也可在理解依赖关系后通过代理引用调用。

- Spring Framework 的接口代理偏好和 Spring Boot 的默认配置不能混为一谈,实际使用哪一种应查看配置和代理类型。

**易错提醒：** 代理性能随版本、调用路径和测试条件变化,不应背固定优劣和百分比。

**具体场景：** 通过接口引用调用 JDK 代理时，调用会进入 InvocationHandler；基于子类的代理依赖方法可覆盖。目标对象内部自调用可能绕开代理，两种方式都应结合框架配置判断。

**追问：代理方法内部调用另一个增强方法会怎样？** 在常见代理模式下，目标对象的自调用可能绕过代理。CGLIB 与 JDK 代理都要考虑这一问题，具体增强还受方法可见性和配置限制。

<span id="58-循环依赖与三级缓存的边界"></span>

### 5 循环依赖与三级缓存的边界

**理解与追问：** 循环依赖能否处理取决于注入方式、作用域、初始化时机和代理等条件。构造器循环依赖尤其难以通过提前暴露解决；工程上优先审视职责拆分，而不是默认依赖容器兜底。

Spring 在允许循环引用时,可通过提前暴露 Bean 引用,解决一部分单例属性注入循环依赖。构造器形成的完整闭环通常在实例尚未创建时就互相等待,无法按这一机制处理。

- 一级缓存 singletonObjects 保存完成创建的单例;二级 earlySingletonObjects 保存早期引用;三级singletonFactories 保存产生早期引用的工厂。

- 典型流程:A 实例化后放入早期引用工厂;A 注入 B;B 创建并依赖 A 时取到 A 的早期引用;B 完成后回填 A,最终 A 完成创建。早期引用可能需要与 AOP 代理协调。

- prototype Bean 的循环依赖不能依赖这套单例缓存处理。部分依赖可用 @Lazy 或 ObjectProvider延迟解析,但前提是不要在构造过程中立即解引用。

- Spring Boot 2.6 起默认禁止循环引用;更稳妥的设计是拆解双向依赖和重新划分职责。

**易错提醒：** 三级缓存不是对所有循环依赖都有效,@Lazy 也不是任意构造器循环的通用修复。

**具体场景：** A 和 B 使用构造器互相依赖时，A 创建前要先构造 B，而 B 又需要 A，通常无法靠提前暴露已实例化对象解决。可考虑拆分职责或调整依赖方向，而不是把三级缓存当万能方案。

**追问：三级缓存能解决所有循环依赖吗？** 不能。构造器闭环、原型作用域以及禁止循环引用的配置都存在限制；优先考虑拆分职责，必要时再明确延迟依赖的生命周期。

<span id="59-spring-与-spring-mvc-的父子容器"></span>

### 6 Spring 与 Spring MVC 的父子容器

**理解与追问：** 父子容器可以用于按层组织 Bean，但子容器与父容器的可见关系并非双向对称。现在的 Spring Boot 应用不一定沿用传统的父子容器划分，应先确认实际启动配置。

传统 Servlet 应用可以用根容器放共享业务和持久层 Bean,用 DispatcherServlet 子容器放控制器等 Web 配置。子容器能查找父容器 Bean,父容器不能反向查找子容器 Bean。

- 这样能隔离多个 Servlet 的 Web 配置,并共享服务和数据访问组件。

- 容器边界有助于分层,但不等于 Java 编译器禁止 Service 引用 Controller。现代 Spring Boot 应用也不一定使用这一父子结构。

**易错提醒：** 父子容器是一种应用配置方式,不是所有 Spring MVC 应用的必备结构。

**具体场景：** 传统 Web 应用可把业务服务放在根上下文，把控制器放在 DispatcherServlet 子上下文；子上下文通常能查找父上下文 Bean。实际 Spring Boot 应用不一定采用这种结构。

**追问：父容器能查到子容器 Bean 吗？** 典型父子上下文中是子可向父查找，父不能反向查找子；但现代应用未必采用这种结构，应先核实实际上下文配置。

<span id="60-mybatis-怎样记录执行耗时"></span>

### 7 MyBatis 怎样记录执行耗时

**理解与追问：** 统计 SQL 耗时可通过 MyBatis 插件拦截合适的执行点，并记录语句标识、耗时与必要的上下文。注意参数脱敏、日志量和异步处理；一次调用耗时也可能包含连接获取等环节。

可实现 Interceptor,在 invocation.proceed 前记录 System.nanoTime,并在 finally 中记录耗时。拦截层次应与想测量的范围一致。

- MyBatis 提供 Executor、StatementHandler、ParameterHandler、ResultSetHandler 四类插件拦截点。

- 拦截 Executor.query 或 update,可记录映射语句执行链路耗时,可能包含缓存命中和结果映射;需要贴近 JDBC 执行时,可选择 StatementHandler 的 query 或 update 等方法。

- 批量更新可能到 flushStatements 才真正发送;应用侧耗时也不等于数据库服务端纯执行时间,应结合数据库慢日志判断。记录语句标识,按阈值采样并脱敏参数。

**易错提醒：** 仅有一条 SQL 日志不能说明数据库用了多久;不要把完整参数无差别写入日志。

**具体场景：** 要监控某 SQL 映射调用，可在 MyBatis Interceptor 中记录开始时间，并在 finally 中记录结束时间和语句标识。该耗时可能包括映射、缓存等环节，需和数据库侧慢日志配合看。

**追问：拦截器里的耗时就是数据库执行耗时吗？** 不一定。不同拦截点可能包含缓存、连接获取、参数处理或结果映射；还要结合数据库侧监控，并避免记录敏感参数。

<span id="61-新增-ioc-di-与-bean-生命周期怎样串起来"></span>

### 8 IoC DI 与 Bean 生命周期怎样串起来

**理解与追问：** IoC 负责对象创建和装配的控制权，DI 是向对象提供依赖的方式。解释生命周期时可按实例化、依赖注入、初始化回调、使用和销毁组织，再结合 BeanPostProcessor 说明扩展。

IoC 把对象创建及依赖管理交给容器,DI 是容器注入依赖的方式。典型 Bean 从定义注册开始,经历实例化、依赖注入、初始化及后处理,必要时包装成代理,最后对外提供服务;容器关闭时执行受管理 Bean 的销毁逻辑。

- 初始化阶段关注 @PostConstruct、InitializingBean.afterPropertiesSet、配置的 init 方法。@PostConstruct 由后处理器触发,不能把它简单当成构造器的一部分;此时不要假定对自身的调用已获得 AOP 增强。

- BeanFactoryPostProcessor 修改 Bean 定义等容器元数据,BeanPostProcessor 处理 Bean 实例及初始化前后逻辑。prototype Bean 创建后通常不由容器自动执行销毁回调,资源需自行管理。

**易错提醒：** 实例化不等于依赖注入和初始化都已完成;容器生命周期也不能替代外部资源的可靠清理。

**具体场景：** 容器先实例化 Bean，再注入依赖，随后执行初始化和相关后处理；服务使用结束、容器关闭时再执行受管理的销毁逻辑。构造器执行完成不等于依赖注入和所有初始化都已完成。

**追问：BeanPostProcessor 和 BeanFactoryPostProcessor 有什么区别？** 前者作用于 Bean 实例的创建与初始化相关阶段，后者主要处理容器元数据。实际执行顺序与扩展点应以版本和配置为准。

<span id="62-新增-spring-单例-bean-为什么不一定线程安全"></span>

### 9 Spring 单例 Bean 为什么不一定线程安全

**理解与追问：** 容器单例只表示该容器中通常复用同一个 Bean 实例，不保证其字段并发安全。把请求数据保存在方法局部变量通常更容易隔离；共享可变字段仍需并发设计。

Spring 的 singleton 表示同一容器内同一 Bean 定义通常共享一个实例,并不自动给方法加锁。多个请求同时操作该实例中的可变字段,仍可能发生覆盖、竞态和可见性问题。线程安全取决于状态与访问方式。

- 业务 Service 通常尽量无状态,把请求数据放方法局部变量或明确的请求上下文;局部变量引用了共享对象时,对该对象的操作仍需保护。

- 确需共享状态时,使用不可变对象、合适的并发容器、原子操作或统一加锁;多实例部署的业务唯一性和状态流转还需数据库等共享资源保证。

**易错提醒：** @Service、@Component、@Transactional 和 singleton 本身都不是共享可变字段的线程安全声明。

**具体场景：** 单例 Service 若把当前用户 ID 放在成员字段中，两个请求可能互相覆盖。将请求专属状态放在方法参数和局部变量更容易隔离；引用指向的共享可变对象仍需保护。

**追问：把变量放进局部变量就一定线程安全？** 局部引用本身由调用栈持有，但它指向的对象仍可能被多个线程共享。应判断共享对象是否可变及所有访问是否遵守同步规则。

<span id="63-新增-spring-aop-怎样工作-常见通知有什么区别"></span>

### 10 Spring AOP 怎样工作 常见通知有什么区别

**理解与追问：** 例如事务、鉴权和审计可通过代理围绕目标方法执行。通知顺序、自调用、异常与返回值处理都受具体切面和代理模式影响，应通过配置和测试确认。

Spring AOP 在符合切点的方法调用外建立代理拦截链,将日志、事务等横切逻辑与业务代码分开。调用进入代理后,按配置执行通知并推进到目标方法,再沿调用链返回;异常也会影响后续通知路径。

- Before 在目标调用前执行;AfterReturning 针对正常返回;AfterThrowing 针对匹配异常;After 具有 finally 语义。Around 可通过 proceed 决定是否及何时继续调用,并处理返回值和异常。

- 多切面的嵌套由优先级等规则控制,进入与退出方向相反。Spring 代理 AOP 主要面向方法执行,和可支持更多连接点的 AspectJ 织入机制有区别。

**易错提醒：** 不能把所有通知背成一条不分正常与异常的固定顺序;Around 吞掉异常还可能改变事务回滚行为。

**具体场景：** 审计切面在调用前后记录信息时，如果 Around 通知没有调用 proceed，目标方法可能根本不会执行。通知吞掉异常还可能让外层误以为操作成功，影响事务处理。

**追问：Around 通知没有调用 proceed 会怎样？** 被包围的后续调用链和目标方法可能不会执行。若吞掉异常或改变返回值，也会影响调用者和事务回滚行为。

<span id="64-新增-spring-boot-自动配置与-starter-是什么关系"></span>

### 11 Spring Boot 自动配置与 starter 是什么关系

**理解与追问：** starter 主要聚合相关依赖与约定，自动配置则根据条件提供 Bean 定义。排查未生效时查看条件匹配报告、类路径、已有 Bean 和配置属性，而不是认为加入依赖就一定启用所有功能。

starter 主要聚合某类功能所需依赖;自动配置则根据类路径、属性、已有 Bean 等条件,决定注册哪些配置与组件。@SpringBootApplication 组合配置声明、自动配置启用及组件扫描等能力。引入依赖并不意味着所有配置都会无条件生效。

- 自动配置先发现候选配置,再用 @ConditionalOnClass、@ConditionalOnMissingBean 等条件筛选;用户自定义组件常能使相应默认配置退让。排查时查看条件评估报告及实际 Bean。

- 现代 Boot 使用 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports 声明自动配置候选,旧版本常见 spring.factories。组件扫描与自动配置导入是不同入口。

**易错提醒：** starter 不等于自动配置代码本身,也不能把某一版本的候选配置文件当作所有版本的固定实现。

**具体场景：** 项目引入某个 starter 后没有出现预期 Bean，可查看条件评估报告：可能缺少类、配置项关闭，或用户自定义 Bean 使默认配置退让。starter 聚合依赖与自动配置条件是两个层面。

**追问：引入 starter 为什么没创建预期 Bean？** 自动配置可能因缺少类、属性或已有用户 Bean 而不匹配。检查条件评估报告和实际配置，不要把依赖引入等同于功能一定开启。

<span id="65-新增-mybatis-参数绑定与字符串替换有什么区别"></span>

### 12 MyBatis 参数绑定与字符串替换有什么区别

**理解与追问：** 参数绑定通常使用预编译参数占位来传值；字符串替换会把文本直接拼入 SQL。动态表名、排序字段等不能简单用值占位时，必须通过白名单约束允许的标识符。

#{} 通常将值映射为 PreparedStatement 的参数占位符,并通过 JDBC 绑定值;${} 则把内容直接拼入 SQL 文本。普通业务值应优先用参数绑定,避免用户输入被当作 SQL 结构执行。两者区别在于参数化与文本替换,不只是是否自动添加引号。

- 表名、列名、排序方向等 SQL 结构通常不能作为值参数绑定;确需动态选择时,由服务端枚举或白名单映射到可信 SQL 片段,不能把请求参数直接塞入 ${}。

- IN 条件的多个值可通过 foreach 生成多个绑定占位符。参数化能防止绑定值改变 SQL 结构,但不会自动修复其他位置的拼接、越权查询或错误业务条件。

**易错提醒：** 用了 MyBatis 不等于天然没有 SQL 注入风险;#{} 也不能直接替代动态表名或列名。

**具体场景：** 查询 `WHERE user_id = #{id}` 时，id 作为参数绑定；若把用户输入直接拼进排序字段或 `${}`，输入可能改变 SQL 结构。动态列名应映射到服务端白名单。

**追问：表名能用普通参数占位符吗？** 参数绑定通常用于值，SQL 标识符不能直接按同样方式绑定。动态表名和排序字段应由服务端白名单映射为可信片段，不能直接拼接用户输入。

## 消息队列与 Kafka

<span id="66-mq-有什么作用-代价是什么"></span>

### 13 MQ 有什么作用 代价是什么

**理解与追问：** 消息队列能够解耦生产与消费、缓冲突发并支持异步处理，但引入消息丢失、重复、顺序和运维成本。是否使用应先明确业务对时效、一致性与失败补偿的要求。

MQ 的主要作用是异步、解耦和削峰:把非必要的同步工作交给消费者处理,让生产者和消费者独立扩缩容,并用队列暂存突发流量。

- 异步:如下单后发送通知,主链路只等待必要步骤完成;需要区分“消息已接收”和“业务已完成”。

- 解耦:生产者发布业务事件,不必直接依赖每个下游服务;事件格式仍需版本管理。

- 削峰:按下游承受能力消费,不能凭空增加处理能力;积压量、消费延迟、保留时间和故障补偿都要监控。

**易错提醒：** 引入 MQ 会带来重复、乱序、积压及最终一致性问题,不能只背三个优点。

**具体场景：** 下单后发通知可通过 MQ 异步处理，减少主链路等待；但如果消费者故障，通知会积压。需要监控积压、设置重试和处理重复消息，队列不能凭空增加下游吞吐。

**追问：MQ 能消除高峰流量吗？** 它只能暂存并平滑处理，不能凭空增加下游容量。持续生产速度高于消费速度时，积压仍会增长，还需关注保留期和故障补偿。

<span id="67-kafka-为什么能够实现高吞吐"></span>

### 14 Kafka 为什么能够实现高吞吐

**理解与追问：** 吞吐来自顺序追加、批量发送、分区并行和操作系统缓存等多方面配合。分区数、消息大小、确认配置和消费处理能力都会影响结果，不能只用“顺序写”解释全部性能。

核心是把大量小请求合并成批量的顺序日志读写,再利用操作系统页缓存、压缩和分区并行,减少磁盘随机访问、网络往返和数据复制。

- 日志追加写:按分区顺序追加;常用数据由页缓存加速,减少直接依赖随机磁盘 I/O。

- 批量与压缩:生产者聚合记录,消费者批量拉取;批次压缩降低传输和存储开销,但批量等待会增加延迟。

- 高效传输与并行:适用路径利用 sendfile 等机制减少用户态与内核态复制;不同分区可分散到不同Broker 并行处理,TLS 等场景会改变传输路径。

**易错提醒：** 不能把“磁盘顺序写一定快于内存随机写”或“所有读写都经过 mmap、零拷贝”当作通用结论。

**具体场景：** 生产者把多条消息合成批次，减少网络往返；不同分区可并行处理。批次等待可能增加延迟，分区过多也有管理成本，需要在吞吐和时延目标下测量。

**追问：分区越多吞吐一定越高吗？** 不一定。分区能增加并行度，但也增加元数据、文件与调度开销；最终瓶颈可能是网络、磁盘、生产端或消费处理能力。

<span id="68-kafka-如何降低消息丢失风险"></span>

### 15 Kafka 如何降低消息丢失风险

**理解与追问：** 分别检查生产端发送确认、Broker 副本持久化配置、消费者处理和提交位点的时机。还要考虑应用崩溃后的重试及重复消费；确认收到消息不等于业务副作用已成功。

按生产、存储、消费三段保证:确认发送结果并可靠补偿,配置副本和确认条件,业务处理成功后再推进消费位点;可靠性必须明确故障范围。

- 生产端:检查 Future 或回调,启用幂等生产;对可重试故障设置退避与 delivery.timeout.ms 总时限,最终失败进入可恢复的补偿流程;业务落库和发消息之间可用事务 outbox。

- 存储端:例如副本因子为 3、min.insync.replicas=2、acks=all;all 等待当前 ISR 中的全部副本,最小 ISR 限制可接受写入的副本数量,不代表只等两个,也不代表全部分配副本。

- 故障切换:避免让缺少已确认记录的副本被不安全选举为 Leader;副本跨故障域部署。

- 消费端:业务成功后提交连续完成位置的下一条 offset;失败重试并做好业务幂等,监控提交失败、积压和数据过期。

**易错提醒：** 无限重试、手动提交或 acks=all 单独使用,都不能承诺任何故障下绝不丢消息。

**具体场景：** 消费者处理订单事件成功后、提交 offset 前宕机，恢复后可能再次收到事件。把业务去重记录与业务变更放在同一本地事务中，可以帮助避免重复副作用。

**追问：消费者先处理后提交位点会怎样？** 若业务成功后、提交前崩溃，消息可能重放，因此业务操作仍需幂等。反过来先提交再处理则可能漏掉业务执行。

<span id="69-kafka-如何保证业务消息的顺序"></span>

### 16 Kafka 如何保证业务消息的顺序

**理解与追问：** 若同一订单的事件必须有序，可以让同一订单标识映射到同一分区，并控制消费处理和失败重试顺序。不同分区之间一般没有全局顺序保证，扩分区也可能改变键的映射。

Kafka 只保证单个分区的日志顺序;要保证同一订单的处理顺序,必须让该订单进入同一分区,并在生产和消费两侧保持业务顺序。

- 生产端:使用订单 ID 等稳定 key 分区;多个生产者同时发送时,Broker 追加顺序未必等于业务先后,必要时增加业务序号。

- 重试:启用幂等并满足客户端配置约束;关闭幂等且允许多个请求在途时,失败批次重试可能导致乱序。

- 消费端:同一分区或同一 key 串行处理;异步多线程不能越过未完成记录提交 offset,扩分区导致key 映射变化时也需迁移方案。

**易错提醒：** 同一分区日志有序不等于多线程业务执行有序,更不等于整个 Topic 全局有序。

**具体场景：** 同一个订单的创建与支付事件使用同一稳定 key 可进入同一分区，但消费者若把两条消息交给不同线程并行处理，支付仍可能先完成。需要按分区或业务 key 约束处理顺序。

**追问：同一个 key 进同一分区就一定业务有序吗？** 还要控制生产先后、消费并发和失败重试；扩分区可能改变映射。多线程异步处理也可能破坏原有执行顺序。

<span id="70-至多一次-至少一次-恰好一次怎么区分"></span>

### 17 至多一次 至少一次 恰好一次怎么区分

**理解与追问：** 至少一次允许重复但努力避免漏处理；至多一次避免重复投递但可能丢失；恰好一次必须明确边界。Kafka 内部事务语义不能自动覆盖数据库或其他外部系统的副作用。

三种语义描述失败重试时的结果:至多一次允许遗漏、避免重投;至少一次允许重复、要求可靠重试;恰好一次要求在明确的事务边界内,业务结果只生效一次。

- 至多一次:先提交 offset 再处理,提交后宕机会跳过未处理消息;生产端不确认、不补发也可能丢失。

- 至少一次:先成功处理再提交 offset,处理成功但提交前宕机会重放;消费者必须用业务唯一键、去重记录或条件更新消除重复副作用。

- 恰好一次:Kafka 读→处理→写回 Kafka,可把输出记录和输入 offset 放入同一事务,并让下游读已提交数据;写外部数据库则需额外协调业务结果与消费进度,例如同一数据库事务内去重。

**易错提醒：** 自动提交开关本身不能定义投递语义,单独保存 offset 或调用 seek 也不能实现端到端恰好一次。

**具体场景：** 先提交 offset 再处理，提交后宕机可能漏处理；先处理再提交，提交前宕机可能重复。所谓恰好一次必须说明边界，Kafka 内事务不自动覆盖外部数据库。

**追问：Kafka 恰好一次能覆盖数据库更新吗？** Kafka 范围内的事务机制不自动把外部数据库纳入同一原子提交。需要结合数据库事务、稳定业务键和去重或可靠消息设计。

<span id="71-kafka-事务消息的核心流程是什么"></span>

### 18 Kafka 事务消息的核心流程是什么

**理解与追问：** 生产者可在事务中发送多个分区的记录，并提交或中止事务；消费端隔离级别会影响是否看到未提交记录。跨外部数据库的原子性还需要额外设计。

Kafka 事务把跨分区写入作为一个提交或中止的整体;用于消费后再生产时,还可以把消费组offset 纳入同一事务,构成 Kafka 范围内的原子处理。

- 生产者配置稳定且不与其他活跃实例冲突的 transactional.id,初始化事务后获取生产者身份和epoch;新的合法实例可隔离旧实例,重启并不表示继续执行原来未完成的事务。

- 业务流程:beginTransaction → 发送记录 → 必要时 sendOffsetsToTransaction →commitTransaction;可中止异常走 abortTransaction,并按异常类型决定重试或终止。

- 事务协调器把状态持久化到 __transaction_state,并驱动相关分区写入 commit/abort marker;下游isolation.level=read_committed 时过滤中止事务,并等待未决事务的可见性边界。

**易错提醒：** Kafka 事务不会自动把 MySQL 写入或第三方接口调用一起提交,事务状态主题分区数也不是固定业务常量。

**具体场景：** 消费 Kafka 消息并向 Kafka 写结果时，可以把输出消息和输入 offset 纳入同一事务；事务提交后，使用相应隔离级别的消费者再读取。外部数据库更新仍需另行协调。

**追问：消费者为什么需要 read_committed？** 如果下游只应处理已提交事务数据，需要采用相应隔离设置；它仍不能让外部支付或数据库调用自动加入 Kafka 事务。

<span id="72-kafka-为什么移除-zookeeper-kraft-做了什么"></span>

### 19 Kafka 为什么移除 ZooKeeper KRaft 做了什么

**理解与追问：** KRaft 使用 Kafka 自身的控制器和元数据日志来管理集群元数据。迁移和支持状态应以具体 Kafka 版本的官方文档为准，不能默认现有集群可直接无风险切换。

KRaft 由 Kafka 的 Controller 仲裁组通过 Raft 复制元数据日志，管理集群元数据。Apache Kafka 4.0 起服务端仅支持 KRaft，ZooKeeper 模式已移除；现有 ZooKeeper 集群需要按其源版本的受支持路径先迁移，不能直接假定升级后可继续使用。详见 [Kafka 4.0 发布说明](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/)。

- Controller 负责 Broker 注册、分区与副本元数据等管理,Broker 主要处理业务数据;控制面与数据面承担不同职责。

- 元数据日志及快照用于传播和恢复集群状态,控制器多数派选举活跃 Controller;运维仍需规划仲裁成员、故障域及恢复流程。

- 消费者 offset 在现代 Kafka 中存于内部主题 __consumer_offsets,不能笼统说一直由 ZooKeeper保存;业务分区副本复制也不能直接等同于 Controller 的 Raft 元数据复制。

**易错提醒：** 移除 ZooKeeper 是架构演进,不能归因为“ZooKeeper 属于 CP,所以性能一定差”。

**具体场景：** KRaft 中控制器仲裁组负责复制和管理集群元数据，Broker 负责业务数据相关工作。迁移时要按当前 Kafka 版本确认支持路径，仍需规划控制器故障域和恢复。

**追问：KRaft 后 Kafka 就没有协调组件了吗？** 不是。元数据由 Kafka 控制器仲裁组管理，只是减少独立 ZooKeeper 的依赖；控制器部署、故障域和恢复仍需要运维设计。
