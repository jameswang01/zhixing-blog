## MySQL 事务 索引与复制

<span id="28-acid-分别靠什么保证"></span>

### 1 ACID 分别靠什么保证

**理解与追问：** 例如转账要求两条余额变更一起提交或回滚，这是原子性；不允许余额突破约束属于一致性。隔离性解决并发事务之间的可见与干扰，持久性还要结合日志刷盘与故障假设说明。

原子性表示事务内操作整体提交或回滚,InnoDB 主要利用 undo 撤销修改;一致性表示提交前后满足约束与业务规则;隔离性由 MVCC 与锁共同实现;持久性主要依赖 redo、提交刷盘及可靠存储。四者相互配合,不能把每个字母机械对应到唯一一种日志。

- 一致性既依赖数据库的唯一键、外键、非空约束与事务机制,也依赖正确的业务逻辑。例如转账不能只扣款而不入账,数据库无法自动识别所有业务约束。

- redo 遵循先写日志再刷数据页的思路,脏页可稍后落盘;崩溃后结合 redo 重放、undo 回滚等机制恢复。持久性保证还受日志刷盘配置和磁盘是否真实完成写入影响。

**易错提醒：** 有 redo 不等于任何配置下已提交数据都绝不会丢,隔离性也不是只靠 MVCC。

**具体场景：** 转账从 A 扣 100、给 B 加 100：两条变更应一起提交或回滚，这是原子性；余额等业务约束属于一致性。数据库日志与事务机制共同参与保证，但不能代替对业务规则的校验。

**追问：有 redo 就一定不会丢已提交数据吗？** 还要看事务提交时日志是否按预期刷盘及存储可靠性。数据库约束只能保证它认识的约束；业务层的总额、状态等规则也需要正确实现。

<span id="29-四种事务隔离级别和三类读异常是什么"></span>

### 2 四种事务隔离级别和三类读异常是什么

**理解与追问：** 用具体时间线说明更清楚：事务 A 两次读取同一行，期间 B 修改并提交，A 若两次结果不同就是不可重复读。隔离级别的实现与幻读边界应结合具体数据库，而不是只背表格。

脏读是读到其他事务未提交的数据;不可重复读是在同一事务内重复读同一行时,看到其他事务已提交的修改;幻读是重复执行同一范围条件时,符合条件的行集合发生变化。InnoDB 默认隔离级别为可重复读。

- 读未提交可能脏读;读已提交避免脏读,但可能不可重复读和幻读;可重复读使普通快照读复用一致性快照,并对需要锁定的范围使用相应锁机制;串行化施加更强约束。

- 串行化不等于整个数据库同一时刻只执行一个事务。它让并发执行的效果满足串行执行要求,冲突访问通常需要等待;是否加共享锁还与语句及 autocommit 有关。

**易错提醒：** 讨论 RR 是否有幻读必须先说明是快照读还是当前读,以及是否混用了两者。

**具体场景：** 事务 A 先查询某账户余额为 100，事务 B 修改为 120 并提交；A 再读到 120 是不可重复读。若 A 以同一范围条件重复查询，第二次多出符合条件的记录，则是讨论幻读的典型例子。

**追问：不可重复读和幻读如何区分？** 前者关注重复读同一行看到别的事务提交的变化；后者关注相同条件下匹配行集合的变化。讨论 MySQL 时还要明确快照读或锁定读。

<span id="30-mvcc-快照读-当前读与间隙锁如何配合"></span>

### 3 MVCC 快照读 当前读与间隙锁如何配合

**按时间线理解（InnoDB，RR）：** 假设账户余额原为 100，事务 A 开始后先做普通 `SELECT`，读到 100 并建立一致性读快照。事务 B 把余额改为 120 并提交后，A 再做普通 `SELECT`，通常仍读到快照中的 100；A 改用 `SELECT ... FOR UPDATE` 时则是锁定读，会按当前状态读取并加锁，可能需要等待其他事务。

这里有两个容易混淆的点：第一，事务自己写入的变化在自己的后续读取中有特殊可见性，不能把快照简单理解为完全冻结的数据库；第二，锁定读究竟锁哪些记录或间隙，取决于隔离级别、命中的索引、查询条件及实际访问路径。参见 [MySQL 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)与[锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)。

**理解与追问：** 在 InnoDB 可重复读下，普通一致性读通常使用事务中建立的快照；SELECT FOR UPDATE 等锁定读读取当前可见记录并按条件加锁。范围访问时的锁还取决于索引、隔离级别和执行计划。

MVCC 利用事务信息、undo 版本链和 Read View 判断可见版本。RC 的普通一致性读每条语句建立新快照,RR 通常在第一次一致性读时建立并复用快照。SELECT ... FOR UPDATE / FOR SHARE 及更新删除按当前状态执行,并按需要加锁。

- 记录锁锁住索引记录;间隙锁限制某个索引间隙的插入;临键锁是记录锁加其前方间隙锁。RR 范围锁定读通常用临键锁防止范围内插入,唯一索引完整等值命中已有记录通常只锁该记录。

- RR 快照读不因别的事务新插入而改变原快照,当前读则使用较新状态;事务还能读到自己修改的数据。混用两种读不能假定所有语句看到完全相同的行集合。长事务会拖延旧版本清理。

**易错提醒：** MVCC 解决可见性问题,不能替代写冲突控制;具体锁范围取决于索引、条件和执行计划。

**具体场景：** RR 下事务 A 普通查询建立快照后，事务 B 更新并提交；A 再做普通查询通常仍读该快照，使用锁定读则按当前状态读取并加锁。具体锁范围还取决于索引和查询条件。

**追问：RR 下所有语句都使用同一个快照吗？** 不能这样说。普通一致性读通常复用快照；锁定读和更新按当前状态执行并加相应锁。自己的修改也可被当前事务看到。

<span id="31-redo-undo-binlog-有什么区别"></span>

### 4 redo undo binlog 有什么区别

**理解与追问：** 可用三个问题区分：崩溃后如何重做已持久化的变更，看 redo；事务回滚或构建旧版本，看 undo；复制与基于日志的数据恢复，看 binlog。它们服务的层次不同，不能相互替代。

redo 是 InnoDB 用于崩溃恢复的重做日志,描述页等存储结构的修改;undo 保存回滚及构造历史版本所需的信息;binlog 位于 Server 层,以语句或行变更事件等形式记录变化,主要用于复制与基于备份的时间点恢复。

- undo 不能简单说成临时日志:事务提交后,更新 undo 仍可能被其他事务的快照使用,要等不再需要时才清理。redo 循环复用,binlog 通常追加并按保留策略清理。

- 追求较强持久性时通常配置 innodb_flush_log_at_trx_commit=1 与 sync_binlog=1。前者为 0 或 2时存在未刷盘窗口,默认约每秒刷盘也不是严格时限;硬件谎报刷盘仍会破坏保证。

- MySQL 通过内部两阶段提交协调 InnoDB 与 binlog 的提交状态;日志也不能替代完整备份。

**易错提醒：** binlog 不能替代 redo 做 InnoDB 页恢复,undo 也不是提交后立刻消失。

**具体场景：** 修改一行时，undo 可用于回滚或构造历史版本；redo 用于崩溃恢复；binlog 用于复制和基于备份的时间点恢复。三者服务的目标不同，不能简单互相替换。

**追问：undo 是不是事务提交后立即删除？** 不一定。其他事务的一致性读可能仍需要历史版本，相关 undo 要到不再需要时才能清理；长事务因此可能拖延版本回收。

<span id="32-b-树与-b-树有什么区别-为什么适合数据库索引"></span>

### 5 B 树与 B+ 树有什么区别 为什么适合数据库索引

**理解与追问：** B+ 树内节点主要用于导航，数据记录或主键关联保存在叶层；叶子之间的有序结构便于范围扫描。实际查询开销还取决于索引覆盖、回表次数与数据分布。

B 树的内部节点和叶子都可以存放数据记录;B+ 树的内部节点主要保存导航键与子页指针,数据记录集中在叶子,叶子按键有序连接。较高扇出有利于降低树高,按页访问减少磁盘 I/O,叶子链也适合范围查询与顺序扫描。

- InnoDB 聚簇索引叶子保存行数据,二级索引叶子保存索引列及主键值。二级索引不能覆盖查询时,通常还要用主键去聚簇索引取其余列,这称为回表。

- B+ 树所有根到叶子的路径深度一致,但查询耗时仍受缓存命中、扫描行数和回表数量影响。内部导航键重复是结构特点,不应概括成“B 树没有冗余,所以更省空间”。

**易错提醒：** 不是所有索引叶子都存完整行,聚簇索引与二级索引要分开回答。

**具体场景：** 查询 `WHERE email = ?` 只返回 email 和主键时，合适的二级索引可能覆盖；如果还要返回未包含的地址字段，通常需要根据主键访问聚簇索引，也就是回表。

**追问：二级索引为什么会回表？** InnoDB 二级索引叶子包含索引列和主键值；查询还需要其他列时，通常要通过主键再访问聚簇索引。若索引已覆盖查询列，可避免这一步。

<span id="33-为什么常用短小-递增的主键"></span>

### 6 为什么常用短小 递增的主键

**理解与追问：** InnoDB 的二级索引记录包含主键值，主键过大会放大其他索引的存储开销。递增键通常有利于减少随机插入带来的页分裂，但也可能形成写入热点，不是无条件最优。

InnoDB 按聚簇键组织行。递增主键让新记录通常落在索引右端,减少随机插入带来的页分裂与搬移;短主键还能减少每条二级索引记录携带主键的空间成本。自增整数因而是常见选择,但应结合写入并发和分布式生成需求决定。

- 随机且很长的主键可能放大索引、降低缓存效率;业务唯一性仍应由独立的业务唯一键保证,不必把所有业务字段放进主键。

- 递增插入并非永远不分裂,也可能形成右端热点。自增值可能因回滚、失败或并发分配出现空洞,不能依靠连续性推断订单数量,也不能直接当作事务提交顺序。

**易错提醒：** 自增主键是常见性能取舍,不是所有业务都必须采用的规则。

**具体场景：** 如果业务为多张二级索引都使用很长的 UUID 主键，每条二级索引记录携带的主键信息也会变大。递增短主键通常改善空间和插入局部性，但可能出现右端热点或 ID 空洞。

**追问：递增主键有什么代价？** 集中追加可能形成右端写入热点，自增值也可能有空洞。分布式环境还需考虑 ID 生成与信息暴露；业务唯一性应由合适的约束保障。

<span id="34-mysql-主从复制怎么工作-为什么会延迟"></span>

### 7 MySQL 主从复制怎么工作 为什么会延迟

**理解与追问：** 主库记录变更日志，从库接收并重放；延迟可能出现在传输、排队或回放阶段。排查时同时看主库写入量、从库执行能力和具体延迟指标，不应只归因于网络。

主库产生 binlog,由发送线程向副本提供日志;副本接收线程把事件写入 relay log,应用线程再重放。现代 MySQL 支持协调线程与多个应用工作线程,不应只背“从库固定两个线程”。传统复制默认异步,所以主库提交与副本可读之间存在窗口。

- 延迟可出现在网络传输、接收落盘或应用阶段。大事务、热点更新、锁等待、磁盘或 CPU 不足、查询争用以及事务依赖限制并行度,都可能导致副本追不上。

- 先检查复制线程、错误、GTID 或位点进度与各工作线程状态,再定位慢 SQL、长事务和资源瓶颈。单独看到 Seconds_Behind_Source=0 不能证明某次刚提交的写入已在该副本可见。

**易错提醒：** 提升版本和增加线程只能改善部分瓶颈,不能消除异步复制的本质窗口。

**具体场景：** 主库已提交一笔订单，副本可能已接收到 binlog，却还在回放此前的大事务。应分别观察日志接收和应用进度，再结合锁等待、磁盘和工作线程状态判断延迟位置。

**追问：副本延迟都由网络造成吗？** 不是。日志接收、落盘和重放都可能成为瓶颈，大事务、锁冲突或资源不足也会造成积压。要分别检查位点及各阶段状态。

<span id="35-主从延迟时-如何保证写后读和业务正确性"></span>

### 8 主从延迟时 如何保证写后读和业务正确性

**理解与追问：** 用户刚修改资料后立刻查看，可以在一段时间内读取主库，或使用具备可验证位点等待能力的方案。等待超时应有降级策略，不能假定所有从库总能及时追上。

先明确要求:可接受短暂旧数据的查询可读副本;订单确认等关键写后读可直接回主库。若要在副本上读到指定提交,可传递该提交的 GTID,在选定副本等待执行完成,再以新的事务或快照读取。等待失败时应回主库或明确重试。

- WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout) 返回 0 表示等待成功,1 表示超时。等待完成后不能继续复用等待前已经建立的 RR 快照,否则仍可能看不到目标提交。

- 半同步通常确认副本已接收并记录日志,不等于已应用且查询可见。Redis 或本地缓存能减轻读压力,但缓存本身可能过期,不能自动修复数据库主从一致性。

- 创建、去重、状态流转应依赖主库唯一约束、原子条件更新或事务锁。读副本“未找到”不能作为允许创建的最终依据;等待可见也不能代替幂等控制。

**易错提醒：** 固定睡几百毫秒、检查一次延迟值或加一层缓存,都不能提供确定的写后读保证。

**具体场景：** 用户刚修改收货地址，随即刷新页面：关键写后读可暂时回主库；若要读副本，可等待对应 GTID 已执行，超时则回主库，并避免复用等待前已经建立的旧快照。

**追问：延迟指标为零就能保证刚写入的数据可见吗？** 不能把单个指标当作目标事务已应用的证明。关键写后读可回主库，或等待目标提交对应位点后使用新的读取快照，并处理超时。

<span id="36-哪些情况可能不使用预期索引"></span>

### 9 哪些情况可能不使用预期索引

**理解与追问：** 索引能否被选择与统计信息、过滤比例、联合索引顺序和查询表达式都有关。先用 EXPLAIN 结合实际数据与执行耗时判断，不要简单认为只要字段建了索引就一定会使用。

常见原因有前导通配符 LIKE、索引列上计算或函数、某些隐式类型或字符集转换、联合索引缺少可用前缀,以及优化器判断扫描成本更低。应区分索引不能有效定位、选错索引与成本上主动不用索引,而不是把所有情况统称“索引失效”。

- 普通 B 树通常能用 LIKE 'abc%' 做范围定位,LIKE '%abc' 通常不能。表达式匹配函数索引或生成列索引时可能仍可利用索引;隐式转换是否影响索引也与转换方向有关。

- 联合索引通常遵循最左前缀;WHERE 条件书写顺序不必和索引列顺序一致。范围条件可能限制后续列继续缩小定位区间,但后续列仍可能参与过滤或覆盖。

- NOT IN、<>、低选择性都不是“一定不用索引”;全表扫描也不一定差,应看实际行数、统计信息和执行计划。

**易错提醒：** 不能只凭 SQL 中出现某个关键字就断言索引必然失效。

**具体场景：** 联合索引 `(a,b)` 中，查询是否能高效定位与使用方式相关；即使范围条件限制了后续列缩小范围，后续列仍可能用于过滤或覆盖。应结合实际参数查看 EXPLAIN，而非只按关键字断言失效。

**追问：出现函数或范围条件就一定不能用索引吗？** 不能一概而论。是否能有效定位与表达式、索引形式和优化器选择有关；范围后续列也可能参与过滤或覆盖。应看真实执行计划。

<span id="37-如何有依据地优化慢-sql"></span>

### 10 如何有依据地优化慢 SQL

**理解与追问：** 先保留原 SQL、参数、执行计划和扫描量，再判断是索引、排序、回表、锁等待还是数据量导致。修改后在可比数据和负载下复测，并留意新索引带来的写入与空间成本。

先从慢日志或监控确认耗时、调用频率、扫描量与返回量,再看执行计划、实际行数、锁等待和资源压力。围绕过滤、连接、排序与返回列设计合适索引,减少无效扫描和回表,最后在代表性数据与负载下验证收益。

- 只查需要的列,能覆盖时争取覆盖;避免无边界查询和过大事务。批量操作减少往返,但批次过大也会放大锁、日志和复制压力,需要实测。

- UNION ALL 仅在不要求去重时替代 UNION;JOIN、子查询、驱动顺序和 GROUP BY 索引是否更优由语义与计划决定,不能套用“连接一定优于子查询”或“小表永远驱动大表”。

- EXPLAIN ANALYZE 会实际执行查询并报告运行情况,应在可控环境使用。索引有写放大与空间成本,不能为所有字段都建索引。

**易错提醒：** 优化要保持结果语义,不能为了更快而改变去重、排序或事务边界。

**具体场景：** 某 SQL 耗时 2 秒，先记录执行计划、扫描行数、实际参数和锁等待；增加索引或改写后，用相近数据量复测，并确认结果语义、写入开销和存储成本没有被忽略。

**追问：为什么新建索引后 SQL 反而变慢？** 可能查询选择了不合适的计划，或新增索引放大了写入与存储开销。保留修改前后的执行计划、扫描行数和实际耗时再判断。

<span id="38-大分页为什么慢-如何优化"></span>

### 11 大分页为什么慢 如何优化

**理解与追问：** OFFSET 很大时，数据库通常仍需跳过前面的记录。稳定排序且允许连续翻页时，可使用上一页最后一个排序键作为游标；如果用户要随机跳到任意页，还需要考虑其他方案。

LIMIT offset, size 通常要先扫描并丢弃 offset 条记录,偏移越大成本越高。连续翻页可改成基于上页最后排序键的游标分页;必须跳页时,可先用覆盖索引取主键,再取当前页完整行,减少丢弃记录时的回表成本。

- 排序应稳定且唯一,例如按 created_at、id 组合排序,并以二者构造下一页条件;建立匹配过滤与排序的联合索引。仅用非唯一时间字段可能漏行或重复。

- 延迟关联仍要付出扫描大偏移的成本,不是复杂度上的根治。游标分页适合前后连续翻页,但不天然支持任意跳页;并发插入、删除和排序字段变化仍须定义分页一致性规则。SELECT id, created_at, title FROM article WHERE created_at < :lastTime OR (created_at = :lastTime AND id < :lastId)ORDER BY created_at DESC, id DESC LIMIT 20;

**易错提醒：** 把 offset 改为 id > 某值前,要确认主键顺序与业务排序一致。

**具体场景：** `LIMIT 100000,20` 通常仍需跳过前面的记录。若按 `created_at,id` 倒序连续翻页，可把上一页最后一行的两个值作为下页游标，并配合匹配的索引与稳定排序。

**追问：游标分页能直接跳到第 1000 页吗？** 通常不天然支持，需要已有游标或其他索引策略。排序键要稳定且具备唯一的次序，例如时间加 ID，并明确并发更新时的分页语义。

<span id="39-新增-innodb-死锁如何形成-定位和处理"></span>

### 12 InnoDB 死锁如何形成 定位和处理

**理解与追问：** 排查死锁要找完整等待环和涉及的索引记录，关注事务语句顺序与范围。即使业务认为操作不同的行，范围锁、多个索引或执行顺序也可能引入额外竞争；重试前要确保事务可安全重放。

死锁是多个事务相互持有对方需要的锁,形成循环等待;普通锁等待则未必存在环。InnoDB 通常启用死锁检测并选择一个事务回滚,应用应识别失败并重试整个事务。排查要把等待链、执行语句、索引及事务边界对应起来,不能只调大超时时间。

- 用 SHOW ENGINE INNODB STATUS 看最近死锁,必要时启用 innodb_print_all_deadlocks 留存错误日志;用 performance_schema.data_locks、data_lock_waits 或 sys.innodb_lock_waits 查当前持锁与等待关系,再结合事务持续时间和语句判断阻塞源。

- 治理重点是统一多行、多表加锁顺序,用合适索引缩小扫描与锁范围,保持事务短小,避免持锁访问慢接口。死锁通常回滚整个受害事务;锁等待超时默认通常仅回滚当前语句,应用应明确回滚或重试边界,并给重试设置次数、退避与幂等约束。

**易错提醒：** 即使只改一行,也可能因多个索引、约束检查等产生死锁;加索引或改为 RC 都不能保证永不死锁。

**具体场景：** 事务 A 先更新记录 1 再更新记录 2，事务 B 反向更新，可能互相等待形成环。应结合死锁日志确认实际索引与锁，再统一顺序、缩短事务，并为可安全重放的事务设置有限重试。

**追问：出现死锁是否只需把超时调大？** 不能。死锁检测会回滚其中一个事务，根因可能涉及多个索引、范围或加锁顺序；应还原等待环、优化事务并对可安全重放的事务做有限重试。

<span id="40-新增-explain-怎么看-覆盖索引-回表和索引下推如何串起来"></span>

### 13 EXPLAIN 怎么看 覆盖索引 回表和索引下推如何串起来

**理解与追问：** 先看访问方式、选择的索引和估计扫描量，再看过滤与额外操作。覆盖索引可减少回表；索引下推可在存储引擎阶段过滤部分条件；实际是否生效要看执行计划与版本。

先看访问方式和实际所选索引,再看预计扫描量、过滤比例及额外操作,判断成本花在扫描、回表还是排序上。覆盖索引让所需列可从索引取得;回表补取其余列;索引下推则先在索引记录上过滤,再决定是否回表,三者解决的问题不同。

- 传统输出关注 type、possible_keys、key、key_len、rows、filtered 和 Extra。possible_keys 是候选,key 才是实际所选;rows 和 filtered 是估算。type=index 可能扫描整个索引,不能只因用了索引就判定高效;结合实际返回量及 ANALYZE 的行数、耗时判断。

- Using index 通常表示覆盖访问;Using index condition 表示 ICP,InnoDB 主要用于需要取完整行的二级索引访问,并不表示无需回表。Using filesort 表示额外排序,不代表一定落盘;Using temporary 表示使用临时表,是否值得优化要看数据规模和实际成本。

**易错提醒：** key_len 不是索引越长越好的评分;覆盖访问也可能因 MVCC 可见性检查需要访问聚簇记录。

**具体场景：** 查询只需索引内已有的列时，可能使用覆盖访问；若要回表，索引下推可先在索引记录上过滤一部分条件。判断时看实际计划，`Using index` 与 `Using index condition` 表示不同含义。

**追问：覆盖索引和索引下推是一回事吗？** 不是。覆盖索引指所需数据可从索引得到，减少回表；索引下推是将可用条件尽早交给存储引擎过滤。实际效果要结合计划判断。
